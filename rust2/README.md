# rust2 — WinuxCmd 2.0 wave1 library-form commands (#1488 pilot)

This directory is the **Rust pilot** for the 2.0 "命令库化" track: commands
implemented as library functions with explicitly injected IO, explicit
env/cwd, no process-global state, and a returned status code instead of
`exit()`. Wave1 covers the 15 inventory wave-1 applets:

```
true false test [ basename dirname printenv pwd
mkdir rmdir readlink realpath chmod chown df
```

Workspace layout (zero external dependencies, std only; MSVC target):

| path | role |
|---|---|
| `crates/winux-core` | the shape contract: `Io`, `EnvSource`, `Ctx`, `CmdResult`, ABI status constant, test support |
| `crates/winux-cmds` | the 15 command library functions + per-command unit tests |
| `crates/winuxcmd-ffi` | C ABI surface (`winuxcmd_run`) with `catch_unwind` at the boundary; built as `cdylib` (host experiments) and `staticlib` (linked into winuxcmd.exe by CMake option `WINUXCMD_ENABLE_RUST2`) |
| `crates/winuxcmd-driver` | thin CLI adapter used by the differential gate (the only code that touches process stdio/env/cwd) |
| `gate/` | three-way differential gate: `run-gate.sh`, case tables (`cases/*.tsv`, generated by `gen-cases.py`), report builder (`make-report.sh`); `gate/wire/` holds the product-wiring matrix probes |
| `GATE-REPORT.md` | results of the last full gate run |
| `REPLACEMENT-RECIPE.md` | how to replace one C++ applet with its rust2 implementation inside winuxcmd.exe (link shape, CMake, bridge, three gates, pitfalls) |

## Shape contract

Every command is a plain function:

```rust
pub fn run(args: &[OsString], io: &mut Io, ctx: &Ctx) -> CmdResult;
```

* **IO is injected.** `Io { stdin: &mut dyn Read, stdout: &mut dyn Write,
  stderr: &mut dyn Write }`. A command never touches process stdio; the
  caller decides buffering and flushing (the driver flushes after dispatch).
* **Environment and cwd are explicit.** `Ctx { cwd: PathBuf,
  env: &dyn EnvSource }`. `EnvSource::get` is exact-name (Windows process
  env lookup is case-insensitive; GNU `printenv gfoo` must not find `GFoo`,
  so the driver's `ProcessEnv` scans the block with exact comparison).
* **No process-global mutable state.** No statics, no thread-locals, no
  CRT fd assumptions. Everything a command needs arrives via arguments.
* **No `exit()`.** The function returns `Ok(status)` (`0` success, `1`
  GNU failure, `2` GNU `test`/`[` syntax error). `Err(CmdError::Io)` is
  reserved for a broken injected handle.
* **Panic boundary.** The cdylib wraps dispatch in
  `catch_unwind(AssertUnwindSafe(..))`; a panicking command becomes status
  `125` (`winux_core::ABI_FAILURE_STATUS`) instead of unwinding into a
  foreign host. The ABI (`winuxcmd_run`) passes argv/envp/cwd as C strings
  and stdin/stdout/stderr as explicit byte buffers (`CBuf`, freed by
  `winuxcmd_free_buf`) — no environment stdio crosses the boundary.

### Why these 15 (wave1)

They are the inventory's wave-1 rows: smallest IO idiom surface
(`win32-console` or none), no global state, no `exit()`-beyond-returning
status, and most already audited clean against GNU in #1462. They exercise
every shape corner the mechanical-replacement recipe needs: pure functions
(`true`/`false`), an expression parser (`test`/`[`), path string processing
(`basename`/`dirname`), env reads (`printenv`), cwd handling (`pwd`),
filesystem mutation (`mkdir`/`rmdir`/`chmod`), link semantics
(`readlink`/`realpath`), account validation (`chown`), and
platform-inherent reporting (`df`).

### Windows pilot subsets (documented deviations)

The gate compares **GNU rc/stdout byte-for-byte** on platform-neutral
cases; where Windows cannot represent POSIX semantics the deviation is
implemented, documented in the module doc comment, and gate-classified:

* `chmod` — NTFS keeps no POSIX bits; the owner-write bit maps to the
  read-only attribute. Mode *parsing* is GNU-exact (octal + symbolic),
  validated before any file is touched, like GNU.
* `chown` — ownership change is a validated no-op. Named accounts resolve
  via `LookupAccountNameW` (the same API family as the 1.x C++ applet);
  unresolvable names fail exactly like GNU (`invalid user` / `invalid
  group` / `invalid spec`).
* `df` — lists ready local volumes (`GetLogicalDrives` +
  `GetDiskFreeSpaceExW` via raw kernel32 FFI, zero crates). Column shape
  mimics GNU (`-h`, `-H`, `-P`); content is platform-inherent.
  `--output` is not implemented (usage error, gate-classified `note`).
* `pwd`/`readlink`/`realpath` output paths in Windows form; the gate
  compares exit status against GNU (`exit` mode) and stdout against the
  C++ exe (`win` mode).
* `test` `-b`/`-p`/`-S` are false (no such device classes on NTFS); `-c`
  recognizes DOS char devices (`NUL`, `CON`, ... and `/dev/null`).

## Streaming stdin ABI (v2, additive; #1488, #1550 follow-up)

### The problem

ABI v1 (`winuxcmd_run`) slurps stdin: the host hands one whole buffer and
the boundary copies it into a `Vec` (`stdin_buf` -> `to_vec()`), so a 64 MiB
input costs a full extra copy at the ABI layer on top of whatever the
command itself accumulates, and "read a chunk, write a chunk" (`cat`/`tr`
class) cannot be expressed at all. Commands that read stdin could not be
wired without turning streaming into slurp-then-run
([REPLACEMENT-RECIPE.md](REPLACEMENT-RECIPE.md) section 5, item 1).

### Choice: pull callback (function pointer + user_data), not a shared ring buffer

Two shapes were on the table; the pull callback is the one implemented.

1. **Pull callback (chosen).** The host registers one "fill this buffer"
   function; Rust calls it synchronously whenever the command asks for more
   input.
   * The rust2 shape contract is synchronous and single-threaded (see
     *Threading model* below). A ring buffer needs a producer on one side —
     a thread plus locks or lock-free indices — and splits buffer ownership
     across two parties with a wakeup protocol. The pull callback keeps one
     thread and one owner per call.
   * The callback maps 1:1 onto `std::io::Read::read` (partial reads are
     legal, `0` is EOF, exactly like `read(2)`). Every command already
     consumes `Io.stdin: &mut dyn Read`, so the whole command layer is
     streaming-capable with **zero command-file changes** — streaming is
     purely an ABI/core/driver property.
   * No ring allocation, no retained pointers: the host owns the buffer for
     the duration of one call, Rust borrows it and forgets it.
2. **Shared ring buffer (not chosen).** It only pays off when a host wants
   overlapped producer/consumer pipelining; nothing in the 2.0 wiring needs
   that. If a host does later, it can layer it *behind* the pull callback
   (the callback is free to serve bytes from a ring filled by another
   thread) — no ABI change required, which is exactly why the simpler
   shape goes first.

### Signature (C form, adopted into `rust2_abi.h` by the v2 bridge adoption)

```c
/* Fill buf (cap bytes, cap >= 1) with the next stdin bytes. Returns:
 *   > 0   bytes filled (may be < cap; partial read is a valid result)
 *   0     end of stream
 *  -1     host stopped feeding: timeout / interrupted (see 124 below)
 *  -2     host read failure (any other negative is reserved, treated as -2)
 * The pointer is borrowed for the duration of the call and never stored. */
typedef long long winuxcmd_stream_read_fn(void* user_data,
                                          unsigned char* buf, size_t cap);

/* Like winuxcmd_run, but stdin arrives through the host callback.
 * stdin_read == NULL means empty stdin (as stdin_buf == NULL in v1).
 * stdout/stderr keep the v1 shape: Rust-owned buffers freed with
 * winuxcmd_free_buf. */
int winuxcmd_run_stream(const char* name, int argc,
                        const char* const* argv, const char* const* envp,
                        const char* cwd,
                        winuxcmd_stream_read_fn* stdin_read,
                        void* stdin_user_data,
                        winuxcmd_cbuf* stdout_buf,
                        winuxcmd_cbuf* stderr_buf);
```

Rust mirror: `winux_core::stream::StreamReadFn` (the fn-pointer type),
`winux_core::stream::StreamReader` (the `impl Read` wrapper), and the
`winuxcmd_run_stream` export in `winuxcmd-ffi`.

**Additive, then one bump at adoption.** While v2 was additive,
`winuxcmd_abi_version()` stayed `1`: v1 symbols and semantics are
byte-for-byte unchanged, and the C++ bridge (`rust2_bridge.cppm`) refuses
on a version mismatch, so bumping from the Rust side alone would break
wired commands. The version went to `2` in the same commit that adopted
`winuxcmd_run_stream` on the C++ side (#1488 v2 bridge adoption: header +
bridge + `WINUXCMD_RUST2_ABI_VERSION` together, per the header's own
rule); it is `3` since the streaming output entry `winuxcmd_run_io`
(see "Streaming output ABI (v3)" below — every bridge entry runs through
it now, with the v2 stdin callback inside the v3 table). The C++ host
entry is the bridge's streaming convenience call
(`run_command_with_stdin_streaming`, real fd 0 through the `file_io` read
path) plus the generic `run_command_with_stdin_source` /
`run_command_with_stdin_bytes`. **Wired commands** (#1488 digest-family
stream adoption): `b2sum`, `sha224sum`, `sha384sum` and `tac` route their
stdin shapes through the streaming entry; every other rust2 command keeps
its v1 behavior. Hosts detect
v2 support by symbol presence
(`winuxcmd_run_stream` in `dumpbin /LINKERMEMBER:1 winuxcmd_ffi.lib`).

### Callback contract

| return | meaning | Rust-side mapping |
|---|---|---|
| `> 0` | bytes filled; **must be `<= cap`**; partial reads legal, no minimum | `Ok(n)` from `Read::read` |
| `0` | end of stream | `Ok(0)` (EOF) |
| `-1` (`STREAM_TIMED_OUT`) | host stopped feeding (timeout / interrupt) | `io::Error` kind `TimedOut`; the run **returns status 124** (below) |
| `-2` (`STREAM_IO_ERROR`) | host read failure (other negatives reserved, same treatment) | `io::Error` kind `Other`; propagates per the command's own contract (e.g. `tac` -> rc 1; a `?`-propagating command -> 125) |

The `StreamReader` wrapper clamps an out-of-contract `n > cap` to `cap`
(defensive; a host that does that is already broken) and never calls the
callback with `cap == 0`. Bytes beyond the returned `n` are not read.

**Timeout convention: 124.** When the host reports `-1` at any point, the
run returns **124** regardless of the command's own status (a command may
have swallowed the read error internally — the flag is tracked at the
wrapper, not inferred from the status). 124 is GNU's convention:
coreutils `timeout(1)` exits 124 when the child times out
(`winux_core::stream::STREAM_TIMEOUT_STATUS`). Partial output written
before the stop stays in `stdout_buf`; the host decides whether to keep it.

### Buffer ownership, lifetime, thread model

* **Ownership.** The callback's `buf` is host-owned memory. Rust borrows it
  for the duration of the single callback invocation and never stores the
  pointer; `user_data` is passed through opaquely and never dereferenced by
  Rust. Output buffers (`stdout_buf`/`stderr_buf`) stay Rust-owned until
  `winuxcmd_free_buf`, exactly as in v1.
* **Lifetime.** The reader lives only inside one `winuxcmd_run_stream`
  call. The host must keep `stdin_read`/`stdin_user_data` valid for the
  whole call and must not free or mutate the buffer concurrently with the
  call.
* **Threading model: single-threaded.** The callback is invoked
  synchronously on the caller's thread, in the order the command reads.
  `StreamReader` holds a raw pointer, so it is `!Send + !Sync` at compile
  time — the streaming run cannot be moved across threads by construction.
  A host that wants a producer thread owns it behind its own callback; the
  ABI makes no thread demands and takes no locks.

### The Windows handle red line (#1487 lesson)

**Rust never touches a CRT fd, process stdio, or a console/pipe HANDLE.**
The host reads its own console/pipe/file and hands over plain byte
buffers; the Rust side sees only the callback and the buffer contents. No
`GetStdHandle`, no `std::io::stdin`, no fd 0 in the library or ABI layer —
the only place process stdio is touched is the CLI driver, whose adapter
exists precisely to convert process handles into the explicit-buffer
protocol (the #1487/#727 root cause was exactly a load-time CRT stdio
binding across the boundary; the streaming ABI adds no new binding).

### Output side

v2 kept the v1 output shape (Rust-owned `CBuf`s drained after the call).
That is superseded by the streaming output ABI v3 below: the C++ bridge
runs every entry through `winuxcmd_run_io`, and `winuxcmd_run_stream`
stays exported with its v2 semantics for other hosts.

## Streaming output ABI (v3, additive; #1488)

### The problem

Up to v2 every rust2 command's stdout/stderr were collected into Rust-owned
`CBuf`s and drained by the bridge only after the command returned. Memory
grew with the output (`seq 1 20000000 | tail -1`: 268 MiB working set,
389 MiB commit for the seq process), nothing appeared until exit (no
`tail -f`, no `tail -f | cut`), a vanished reader never stopped a producer
(`seq inf | head -1` allocated until the 32 GiB request aborted the
process), and the relative order of stdout and stderr was lost (stdout was
always drained first).

### Signature (`src/shared/rust2_abi.h`)

```c
/* Write len (>= 1) bytes. Returns 0 = all written; -1 = broken pipe (the
 * reader is gone); -2 = other write failure (the host recorded the Win32
 * cause; any other non-zero value is reserved, treated as -2). */
typedef int winuxcmd_stream_write_fn(void* user_data,
                                     const unsigned char* buf, size_t len);

#define WINUXCMD_IO_STDOUT_LINE_BUFFERED 0x1u

struct winuxcmd_io_v3 {
  winuxcmd_stream_read_fn* stdin_read;   void* stdin_user_data;
  winuxcmd_stream_write_fn* stdout_write; void* stdout_user_data;
  winuxcmd_stream_write_fn* stderr_write; void* stderr_user_data;
  unsigned flags;
};

int winuxcmd_run_io(const char* name, int argc, const char* const* argv,
                    const char* const* envp, const char* cwd,
                    const struct winuxcmd_io_v3* io);
```

NULL `stdin_read` = empty stdin (the v2 contract, unchanged); NULL
`stdout_write`/`stderr_write` = discard; a NULL `io` is an all-NULL table.
Rust mirror: `winux_core::stream::{StreamWriteFn, HostWriter, LineSplit,
StdoutWriter, stdout_writer, IO_STDOUT_LINE_BUFFERED,
STDOUT_BUFFER_CAPACITY}` and `winuxcmd_ffi::{WinuxcmdIoV3,
winuxcmd_run_io}`. `winuxcmd_abi_version()` and
`WINUXCMD_RUST2_ABI_VERSION` are 3 (bumped together); v1 `winuxcmd_run`
and v2 `winuxcmd_run_stream` stay exported with unchanged semantics.

### Contract

| callback return | meaning | the command sees |
|---|---|---|
| `0` | all `len` bytes written | `Ok(len)` |
| `-1` | broken pipe: the reader is gone | `io::ErrorKind::BrokenPipe` |
| `-2` (and any other non-zero) | other write failure | `io::Error::other` |

* **Sticky failure.** `HostWriter` remembers the first failure; every
  later write on that stream fails at once with the same kind and **never
  calls the host again** — an unbounded producer (`seq inf`, a `shuf -r`
  loop) stops at its next write, whatever it does with the error.
* **Ownership.** The bytes handed to a write callback are Rust-owned and
  borrowed for that one call; the host writes or copies them before
  returning and never stores the pointer. `user_data` is never
  dereferenced by Rust.
* **Threading.** Every callback (stdin, stdout, stderr) is invoked
  synchronously on the caller's thread, in program order; the writers hold
  raw pointers, so they are `!Send + !Sync` by construction (v2 model).
* **Windows red line.** Unchanged: Rust never touches a CRT fd, process
  stdio or a console/pipe HANDLE; the host writes its own handles.

### Buffering policy

* **stdout, `flags & WINUXCMD_IO_STDOUT_LINE_BUFFERED`** (the bridge sets
  it iff stdout is an interactive console): `std::io::LineWriter`
  (64 KiB) over `LineSplit`, which hands **each complete line to its own
  callback** — a multi-line write (seq's chunked output) becomes one
  callback per line, so a console sees every line the moment it is
  complete (C stdio `_IOLBF`). A partial line waits for its newline, a
  full buffer, or the final flush.
* **stdout otherwise** (pipe, file, NUL, daemon capture): `BufWriter`
  with 64 KiB capacity; a write larger than the buffer goes straight to
  the host (no extra copy for seq's 1 MiB chunks).
* **stderr: unbuffered** — every command write is one callback (GNU
  stderr), so a diagnostic reaches the host before stdout bytes the block
  buffer still holds.
* **Flush.** The boundary flushes stdout after the command returns
  (inside `catch_unwind`) and, best-effort, after a contained panic.

### Status

`winuxcmd_run_io` returns exactly what v2 returns: the command's own
status, 124 when the stdin callback reported `-1`, 125 on panic /
unknown command / `CmdError::Io`. Write failures do **not** change it at
the ABI — the host saw every callback result and applies its own mapping.
The C++ bridge (`rust2_bridge.cppm` `run_io`) maps:

* **any stdout `-1` -> 141**, silently, overriding the command's status:
  GNU dies of SIGPIPE at that write and the shell reports 128 + 13; the
  product's emulation of that death is 141 (#1142, `yes.cpp`
  `kSigpipeDeathStatus`). Known consequence: a command that *ignores*
  SIGPIPE under GNU (`tee -p`, `tee --output-error=warn`) still ends 141
  here (GNU: 0 / 1) — the boundary has no per-command opt-out.
* **any stdout `-2` -> the #1368 close_stdout contract**: the command
  produced stdout bytes against a closed (`>&-`, a closed CRT fd 1 —
  reported without a write attempt, exactly the old drain's trigger) or
  failing stdout, so the bridge prints `<name>: write error: <reason>`
  once and returns 1 (`Bad file descriptor` for the closed fd, else the
  console layer's `stdout_write_error_text()`). A command that wrote
  nothing never reaches a callback and keeps its status (`true >&-` rc 0).
  When the command already reported the failure itself on stderr after
  the `-2` (tac's and tee's write-error paths), the bridge adds no second
  diagnostic and keeps the command's failing status (1 if it returned 0).
* stderr `-1` (stderr pipe gone) never changes the status.

The console face carries a chunk's trailing incomplete UTF-8 sequence into
the next chunk, so `WriteConsoleW` never converts half a character (pipes
and files get the bytes unchanged).

## Out of scope for this pilot

* No `chmod`/`chown`/`df` full POSIX semantics. (Wiring into the dispatcher
  started with the replacement wave; see the recipe.)
* Symlink-creating setups need Developer Mode; without it the gate runs
  link-sensitive cases in `win`/`exit` classification only.
* The digest family (`b2sum`, `sha224sum`, `sha384sum`) and `tac` ARE
  wired through streaming stdin since the #1488 digest-family adoption,
  and `expand`, `join`, `numfmt`, `tsort`, `unexpand` since the v3 bridge
  switch retired the `kRust2StdinCommands` slurp; the remaining
  whole-buffer stdin consumers (`base64`, `base32`, `fmt`, `fold`,
  `paste`, ...) stay on `run_command_with_stdin` (slurp, then served from
  host memory through the v3 stdin callback) until their wave. Output is
  streamed for every wired command.
