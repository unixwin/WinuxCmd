**三句话结论**

1. **命令面本身是干净的**：default = 178 − 6 = 172，full = 178，差集与
   `winux_edition::kFullOnlyCommandNames` 逐名一致；172 个入口 `--help` 全部

   "default 一个不少、full 一个不多" 在**注册面/物化面**成立。
2. **物化落点有 P1 缺陷**：归档解包后按 README 的"cd usr/bin; .\create_links.ps1"
   执行，172 个入口全部落到 `usr/bin/usr/bin/` 里（且把 `bin/ dev/ etc/ opt/ usr/ var/`
   这套布局建在 `usr/bin` 内）。命令一个没少，但**一个也不在 PATH 上**。
   安装器路径（ISS 显式传 `{app}`）不受影响，所以 CI 从未覆盖到这条路径。
3. **default 面建议维持 172，新增裁撤 3 名（`chroot` `chcon` `runcon`）+ 2 名待裁
   （`mkpasswd` `mkgroup`）**，即建议定稿 default = 167（裁定若否决 2 名则为 169）。
   理由见 §4；裁动只动 `kFullOnlyCommandNames` 一处。

同时发现 4 类文档/C I 面的漂移（env 仍在 5 处名单里、单一真源指向不存在的
`src/core/package_edition.h`、CI marker 硬编码 `commands=true;false`、
wpm-source 索引 job 的 needs 级联），见 §6/§7。

## 2. 命令面全集盘点（含 rust2 接线后的增减）

### 2.1 注册面 178 的构成


- 扫得 **178 个文件 → 178 条注册 → 178 个唯一命令名**（每文件一注册，无重名）。

## 3. 逐物化核对（CPack 产物 → 首次运行 → census）

### 3.1 方法（可复现）

CI 产物本身不携带 per-command exe，所以"产物 manifest"= **归档内容 + 首次物化后的
`usr/bin` 全集**。核对分两段：

```powershell
# A. 归档内容（= CI 的 CPack 产物，本地同参数重建）
cmake -S . -B build-ed-default -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_MODE=RELEASE -DUSE_STATIC_CRT=ON -DENABLE_TESTS=OFF \
  -DWINUXCMD_ENABLE_RUST2=ON
cmake --build build-ed-default --parallel
cd build-ed-default ; cpack -G ZIP -C Release ; cpack -G 7Z -C Release
# → WinuxCmd-1.2.1-win-x64.zip

# B. 首次物化（README/Release notes 的官方步骤）
Expand-Archive WinuxCmd-1.2.1-win-x64.zip -DestinationPath stage
cd stage\WinuxCmd-1.2.1-win-x64\usr\bin
.\winuxcmd.exe wpm links rebuild --root ..\..      # 正确 root（等价于 ISS 的 {app}）
dir *.exe                                          # census
```

`-DWINUXCMD_PACKAGE_EDITION=full` 重复一遍得到 `-full` 归档。

### 3.2 原始数字

| 测量 | default | full |
|---|---:|---:|
| 归档条目数 | 13 | 13 |
| 归档内 `.exe` | 2（winuxcmd, winuxcmd-shim） | 2 |
| `wpm links rebuild` 输出 | `links created=172 unchanged=0 stale_removed=0 failed=0` | `links created=178 ... failed=0` |
| `usr/bin` 内 `.exe` 总数 | 174 | 180 |
| 命令入口（扣 winuxcmd/shim） | **172** | **178** |
| 与注册面差集 | 缺 `[ false kill test time true`（6 名，符合名单） | 与 178 注册名逐名相等（`comm -3` 空） |
| 遗留名 `jq`/`link` | 不存在 | 不存在 |
| `env.exe` | **存在**（#1627 回归生效） | 存在 |
| 172 个入口 `--help` | **172/172 rc=0** | — |
| 6 个 full-only 的 verb 形式 | `winuxcmd kill --help` 等 6/6 rc=0（`false --help` rc=1，与 GNU 一致，已用 WSL oracle 复核） | 入口直调 |

结论：**default 该有的一个不少（172/172），full 一个不多（178/178，无多余名）**；
两 edition 差集精确等于声明名单；arm64 与 x64 面不可能分叉（`src/commands/` 与
`src/core/` 里没有任何 arch 条件注册，`rust2-surface-check` 的 marker 相等断言覆盖）。

### 3.3 **P1 缺陷：官方步骤的物化落点错位**

README（"Navigate to the `usr/bin` directory → Run `create_links.ps1`"）与 Release
notes 指向的脚本，在归档树上实跑结果：

```
cd ...\WinuxCmd-1.2.1-win-x64\usr\bin
.\create_links.ps1
wpm: links created=172 unchanged=0 stale_removed=0 failed=0     ← 成功
dir *.exe                                                       ← 只有 2 个 exe
dir /s /b usr\bin\*.exe                                         ← 172 个全在 usr\bin\usr\bin\
```

且 `usr/bin` 下被建出 `bin\ dev\ etc\ opt\ usr\ var\` 六个布局目录。

**根因（两处，叠加）**：

1. `scripts/create_links.ps1:47-52`：

   ```powershell
   $binDir = Get-Location
   $root = if ($binDir.Name -eq "bin" -and $binDir.Parent.Name -eq "usr") {
       $binDir.Parent.Parent
   } else { $binDir }
   ```

   `Get-Location` 返回的是 `System.Management.Automation.PathInfo`，**没有
   `.Name` / `.Parent` 属性**（PS 5.1 与 PS 7.7 实测均为空），条件恒假 →
   `$root` = 当前目录（`...\usr\bin`）。该写法是 `3e1090e1`（2026-08-15
   "Install WinuxCmd into the real usr/bin tree"）引入的，在此之前的
   `$root = Get-Location` 恰好能工作。
2. `src/commands/wpm.cpp:6140-6152`：`--root` 原样使用，不做"bin/usr 折叠"
   （`default_root()` 从 exe 路径推断时**有**这套折叠，显式 `--root` 没有）。
   `canonical_bin_dir(root) = root/usr/bin`，于是 `root = ...\usr\bin` 时入口
   落到 `...\usr\bin\usr\bin`。

**影响面**：只影响归档（zip/7z/tgz）用户第一次手动物化；ISS 安装器走
`wpm links rebuild --root {app}`，root 正确，不受影响——这正是 CI 一直绿的原因。
niubash 捆绑包也传正确 root，不受影响。

**修法**（草稿见 PR 文件）：
- `create_links.ps1` 用字符串路径判目录名（`Split-Path -Leaf`）；
- `wpm.cpp` 把 `default_root()` 的折叠逻辑提成 `fold_bin_dir()`，显式 `--root`
  也走一遍（对第三方 launcher 的防御，不依赖调用方修好）。

## 4. default 面建议定稿

### 4.1 原则（本审计采用）

1. **GNU 用户日常面**：Linux 上一条普通构建/脚本用到就保留。
2. **无特权依赖**：不需要提权就能做成事，或至少按 GNU 措辞优雅降级。
3. **无平台家族阻塞**：不做"在 Windows 上 100% 失败"的入口（`winuxcmd <name>`
   verb 形式仍然可用，作为兼容垫片）。
4. **默认版是"零解释成本"面**：入口出现在 PATH 上，就代表"这条命令能跑"。

### 4.2 裁动表

> 只列**变动项**；其余 167 名一律 keep（全量表见 §4.4）。
> 裁 = 从 default 入口面移除（进 `kFullOnlyCommandNames`），命令本体在
> 多合一二进制里保留，verb 形式照旧。

| # | 命令 | 现状 | 建议 | 依据（实测/源码） | 风险 |
|---:|---|---|---|---|---|
| 1 | `chroot` | default | **裁 → full** | 占位实现：唯一路径是无条件 `chroot: changing the root directory is not supported on Windows`，exit 125（`src/commands/chroot.cpp:63-67`）。违反了"入口即能力" | 低。Linux 脚本里的 `chroot` 在 Windows 上本来必然失败；verb 仍给同一条明确消息 |
| 2 | `chcon` | default | **裁 → full** | 无条件 `chcon: SELinux file contexts are not supported on Windows`，exit 1（`chcon.cpp:155-169`），无任何成功路径 | 低。SELinux 语义在 Windows 不存在 |
| 3 | `runcon` | default | **裁 → full** | 无条件 `runcon: failed to get current context: SELinux is not supported on Windows`，exit 1（`runcon.cpp:72-79`） | 低，同上 |
| 4 | `mkpasswd` | default | **裁 → full（待裁）** | **不是 GNU mkpasswd**：这是 MSYS 语义的 Windows 账户库导出（`mkpasswd -c` → `cmx:*:197609:...`）。GNU/util-linux 的主要用法在这里直接失败：`-m` → `invalid option -- 'm'`，`-S` → `--method is not supported on Windows`。同名不同物是比"缺命令"更坏的体验（脚本可能把账户库写进密码字段） | 中。MSYS2 用户可能习惯 `mkpasswd -l`；裁撤后 verb 形式仍可用，迁移指南需点名 |
| 5 | `mkgroup` | default | **裁 → full（待裁）** | 同上：输出 Windows 组库（`None:*:197121:` 等），GNU 无此命令 | 中，同上 |
| — | `env` | default | keep（**已修**） | #1627：env 不是 bash 内建，`#!/usr/bin/env bash` 的 hook 依赖它 | — |

裁后数字：**default 172 → 169（若否决 4/5）→ 167（若全裁）**，full 仍 178。
名单变成 6+3=9 名或 6+5=11 名，仍只改 `kFullOnlyCommandNames` 一处。

### 4.3 明确**不裁**的边界（负面清单）

| 命令 | 为什么看起来该裁 | 为什么不裁 |
|---|---|---|
| `chown` | 改属主需 `SeRestorePrivilege`/`SeTakeOwnership`（`chown.cpp:999-1000,1113`，`chgrp.cpp:450,659`） | 无特权时**按 GNU 措辞降级**（实测 `chown Administrator f` → `chown: changing ownership of 'f': Operation not permitted`，exit 1），自有文件 `chown $(whoami) f` → rc 0。构建脚本普遍 `chown -R`，有明确报错优于 command-not-found |
| `chgrp` | 同上 | 同上：自有组可改，跨组按 GNU 措辞失败 |
| `mknod` | 设备节点在 Windows 不存在 | `p`（管桥 #1038）**可用**；`b`/`c` 报 `Operation not permitted`——与 GNU 在无权限/不支持文件系统上的措辞一致。属"平台家族已裁定"（WP-J wave-W4） |
| `mkfifo` | 同上 | 管桥可用，POSIX 脚本常用 |
| `chmod` | 权限模型不同 | 实测 `chmod 444` → 只读属性生效（append 被拒），`chmod 644` 恢复；这是 Windows 上唯一可行的映射 |
| `getfacl` | 只有读、没有 `setfacl` | 只读 ACL 诊断本身有价值；缺配对是"半套"，建议 2.0 文档写明（不裁） |
| `ldd`/`pldd` | glibc ELF 语义 | 本实现列 PE 导入/模块，功能真实存在 |
| `killall`/`pkill`/`pgrep`/`pidof` | 与 `kill`（full-only）同类 | 这些**不是** shell 内建，PATH 上没有同名遮蔽；`kill` 之所以 full-only 是因为 bash 内建拥有其语义 |
| `egrep`/`fgrep` | GNU 3.8 起废弃 | GNU 仍然发这两个入口（带废弃警告）；保留 compat 面，grep wire 时须一并接线（见 §4.5） |
| `cygpath`/`regtool`/`d2u`/`u2d`/`dos2unix`/`unix2dos`/`tzset`/`mpicalc`/`wpm` | 非 GNU 命令 | WinuxCmd 的自有面/桥接面，是产品价值的一部分；但 `tzset` 是 glibc 函数名，建议 2.0 文档标注"Winux 自有，非 GNU" |

### 4.4 全量定稿表（178）

见文末附录 A。

### 4.5 未来改动对 edition 面的影响（给后续 wire 的约束）

- **grep wire（#1660）**：`egrep`/`fgrep` 是**独立注册**（`grep.cpp:3073/3086`）。

## 5. installer / CPack 面核对

### 5.1 现有链路（三入口，一个物化算法）

```
CPack ZIP/7Z/TGZ ──> 解包 ──> create_links.ps1 ──┐
Inno Setup (ISS)  ──> {app} ──> [Code] CreateCommandLinks ──┤──> winuxcmd.exe wpm links rebuild
wpm / niubash     ──> --root  ──────────────────────────────┘        (唯一物化算法)
```

- `CPack`：`install()` 只装 `winuxcmd.exe`、`winuxcmd-shim.exe`、5 个脚本、
  README×2 + LICENSE；`install(CODE)` 剥掉 PCRE2 SDK 树（`CMakeLists.txt:235-266`）。
  实测归档 13 条，无 `include/lib/share/pcre2-config`，无 per-command exe —— 符合设计。
- `CPACK_PACKAGE_FILE_NAME` 走 `WINUXCMD_PACKAGE_ARCH`（Uarz 先例
  `4285c78b`/`f3d64ac9`，CPack 显式 arch，不信 `CMAKE_SYSTEM_PROCESSOR`），
  再加 `WINUXCMD_PACKAGE_EDITION_SUFFIX`（`-full`）。当前实现已吸收该先例。
- `ISS`：`[Files] Source: {#StageDir}\*; DestDir: {app}`；`[Code] CreateCommandLinks`
  调 `wpm links rebuild --root {app} --force`；安装器只在 default edition 构建
  （`if: matrix.edition == 'default'`）。**没有第二份命令名单**。

## 6. wpm-source 索引 job：SKIPPED 根因与恢复

### 6.1 事实

| 运行 | 触发 | `release` | `update-wpm-source-index` |
|---|---|---|---|
| 43575540984（main push，4 leg 全绿） | push/main | skipped | **skipped** |
| 43575862627（main push，rust2-gate/rust-tests 红） | push/main | skipped | **skipped** |
| 41336205152（v1.2.0 tag，两个 full leg 红） | push/tag | skipped | **skipped** |
| 41339117246（v1.2.0 tag 重跑，全绿） | push/tag | success | success（PR #109 自动建+合） |
| 41377032409（v1.2.1 tag，全绿） | push/tag | success | success（PR #110 自动建+合） |

### 6.2 根因（三层，按严重度）

1. **`needs: release` 的级联跳过**（真因）。job 定义
   （`.github/workflows/build-winuxcmd.yml:869-877`）：

   ```yaml
   update-wpm-source-index:
     needs: release
     if: github.ref_type == 'tag' && startsWith(github.ref_name, 'v')
   ```

   GitHub 的 `needs` 语义：上游 `skipped`/`failed` → 本 job **skipped**（`if`
   不再求值，除非写 `always()`）。而 `release` 又 `needs: [build-windows,
   rust2-surface-check]`。于是：
   - 任何 **非 tag 运行**（main push / PR，即仓库里 99% 的运行）→ `release`
     skipped → index job skipped。Actions UI 上每天看到的 "Skipped" 就是这个，
     **属预期**，但会掩盖真故障。
   - **tag 运行里任何一个 build leg 红** → `release` skipped → index job
     **静默 skipped**（v1.2.0 首跑就是如此）。release 自身也 skipped，
     但人工重跑 tag 才会恢复——没有任何"索引待补"的信号。
2. **只有 tag 一个入口**：workflow 声明了 `workflow_dispatch`，但这个 job 的
   `if` 要求 `github.ref_type == 'tag'`，手动触发时 `ref_type` 是 `branch` →
   永远 skipped。**发布后若索引漏更/合错，除了重新打 tag 没有恢复手段**。
3. **版本号来源绑在 `release.outputs`**：`needs.release.outputs.version` 来自
   `release` 的 `final_version` step。即使加 `always()`，上游 skipped 时 outputs
   为空，脚本会拿到空 `--Version`（`update-wpm-source-index.ps1` 的正则会抛
   "Invalid version ''"）。

补充事实（不是 skip 原因，但同一条链上的可靠性缺口）：PR 步骤用
`gh pr list ... --jq '.[0].url'`，空列表时可能得到字符串 `null`，
`[ -z "null" ]` 为假 → 跳过 `gh pr create` → `gh pr merge null` 失败。
v1.2.1 的成功日志里 `gh pr create`/`merge` 的输出确实没有出现在 job log，
只有分支推送（PR #110 的 created/merged 时间在 job 窗口内），说明这条路径
**依赖 gh 的隐式输出**，没有显式校验。

### 6.3 恢复方案（草稿，见 PR 文件）

```yaml
update-wpm-source-index:
  needs: [build-windows]           # 不再依赖 release：产物来自 build-windows
  if: >-
    always() &&
    (needs.build-windows.result == 'success') &&
    (github.ref_type == 'tag' && startsWith(github.ref_name, 'v') ||
     github.event_name == 'workflow_dispatch')
  with:  # workflow_dispatch 输入，见下
```

- **版本号自取**：`VERSION="${GITHUB_REF#refs/tags/v}"`（与 `release` 同款），
  `workflow_dispatch` 时取 `inputs.version`；不读 `needs.release.outputs`。
- **产物来源**：`build-windows` 的 artifact（`retention-days: 1`，同一次运行内
  有效），不再经过 `release`。
- **manual 恢复入口**：`workflow_dispatch` 增加 `version`（可选）与
  `dry_run`（只算不推）输入，输出一份 sha256/尺寸对照，便于 WP-S 第 5 步
  "确认执行"。
- **严格 PR 校验**：
  ```bash
  pr_url="$(gh pr list ... --json url --jq '.[0].url // empty')"
  [[ "$pr_url" == https://github.com/unixwin/wpm-source/pull/* ]] || pr_url="$(gh pr create ...)"
  gh pr merge "$pr_url" --squash --delete-branch
  state="$(gh pr view "$pr_url" --json state --jq .state)"
  [[ "$state" == "MERGED" ]] || { echo "::error::wpm-source PR not merged ($state)"; exit 1; }
  ```
- **可见性**：给 job 加一个 `summary`（`$GITHUB_STEP_SUMMARY`）写
  `version / sha256(x64,arm64) / size / PR URL`，发布后一眼能核。
- **索引内容不变**：仍只索引 default edition（full 永不入索引），`files` 仍只有
  `winuxcmd.exe` / `winuxcmd-shim.exe`（脚本里 `Assert-ArchiveCarries` 已守）。

**验证方式（不重打 tag）**：用 `workflow_dispatch` + `version=1.2.1` +
`dry_run=true` 跑一次，应输出"索引已是 1.2.1"或给出差异；再用
`version=1.2.1` 实跑，应走 "git diff --quiet → already matches" 早退（不产生空 PR）。
