# 2.0 — locale-database simulation layer (design)

Status: implemented core subset (this branch, `rust2/locale-db`), tracked by
issue #1549 (parent #1488). Supersedes the `keyword_value()` lookup table in
`src/commands/locale.cpp`.

## 1. Problem

`locale(1)` answered every NAME operand from a hard-coded table in
`src/commands/locale.cpp` (`keyword_value()`, 25 keywords). Every value was a
C-locale/en-US hybrid: `int_curr_symbol` = `USD `, `currency_symbol` = `$`,
`frac_digits` = `1`, `yesstr` = `yes`, `day`/`mon` English, `charmap` from a
two-branch environment probe. Consequences measured against glibc 2.39:

```
# glibc C locale          # WinuxCmd before this change
frac_digits=-1            frac_digits=1
currency_symbol=""        currency_symbol="$"
yesstr=""                 yesstr="yes"
decimal_point="."         decimal_point="."      (agrees by accident)
```

and `date +%x/%X/%c` always used the C-locale forms, regardless of the locale
the environment selected (or the Windows user locale). There is no notion of a
*locale database*: each keyword was a literal, so `-a`/`-m` inventories,
per-category dumps and any locale other than C could only ever be special-cased.

## 2. Scope

In scope (this round):

- LC_CTYPE codeset: `charmap` (and the underlying codeset model).
- LC_NUMERIC: `decimal_point`, `thousands_sep`, `grouping`.
- LC_MONETARY: all 15 `lconv` monetary fields exposed by glibc `locale -k`.
- LC_TIME: `day`/`abday`/`mon`/`abmon`/`am_pm`/`d_fmt`/`t_fmt`/`d_t_fmt`/
  `t_fmt_ampm`, consumed by `date` for `%a %A %b %h %B %p %P %r %x %X %c`.
- C/POSIX synthesis (exact glibc C-locale values) and failure fallback.
- Per-category environment resolution: `LC_ALL` > `LC_<CATEGORY>` > `LANG` >
  Windows user default.

Out of scope (documented remaining work, §12): `-a`/`-m` inventories from the
Windows NLS catalogue, per-category raw value dumps (`locale LC_CTYPE`),
LC_PAPER/LC_NAME/LC_ADDRESS/LC_TELEPHONE/LC_MEASUREMENT/LC_IDENTIFICATION
items, `yesstr`/`nostr` (no Win32 data source), message translation
(`WINUX_LANG`, owned by `src/utils/i18n.cppm`), collation.

## 4. Architecture

```
        POSIX spelling                      Win32 NLS                      POSIX projection
  ┌──────────────────────┐          ┌────────────────────────┐        ┌──────────────────────────┐
  │ LC_ALL/LC_TIME/LANG  │          │ GetLocaleInfoEx(W)     │        │ lconv-shaped Numeric /    │
  │ "zh_CN.UTF-8@mod"    │─resolve─▶│ LOCALE_S*/LOCALE_I*    │──────▶ │ Monetary, strftime-shaped │
  │ "C", "POSIX", ""     │  name    │ GetCPInfo              │        │ Time, Codeset, ctype bits │
  └──────────────────────┘          │ GetUserDefaultLocaleName│       └───────────┬──────────────┘
                                    │ GetStringTypeW         │                    │
                                    └────────────────────────┘                    ▼
                                                                    locale(1)  date(1)  [future]
```

Three stages, each independently testable:

1. **Name resolution** turns the POSIX spelling into either the synthetic C
   locale or a Windows BCP-47 name. Never silently substitutes a different
   locale: a name that does not resolve is reported by lookup failing into the
   C record and the caller keeps the requested spelling in `LocaleValues::name`
   (`resolved=false`).
2. **Data acquisition** is the only place that calls Win32. Every field is
   read through one helper that handles the two-call size protocol, `0`
   returns, and number/string distinction.
3. **Projection** converts Win32 shapes into POSIX semantics: `INEGCURR`
   format code → `n_cs_precedes`/`n_sep_by_space`/`n_sign_posn`; `SGROUPING`
   `"3;0"` → POSIX grouping bytes; Windows date/time pictures → `strftime`
   patterns; day-of-week Monday-first → POSIX Sunday-first.

`module utils:locale_db` (`src/utils/locale_db.cppm`) exports the value types
and the cache; it has no output, no I18N text and no process state beyond the
immutable cache. Consumers (`locale.cpp`, `date.cpp`) own rendering.

Cache: one `unordered_map<canonical POSIX name, LocaleValues>` guarded by a
mutex, filled lazily and never erased. The record is built *outside* the lock
(duplicate work on a race is harmless; `emplace` keeps the first), and
references returned by `lookup()` stay valid for the process lifetime because
node-based rehashing does not invalidate them. The key is the canonicalized
spelling including the codeset (`en_US.UTF-8` and `en_US` are different
records; `zh-CN` and `zh_CN` are the same), so a command that asks for the
same locale per `strftime` specifier pays one Win32 round-trip per field for
the whole process — `date` formats with a cached record, not per call. There
is no TTL and no invalidation: the NLS database does not change under a
running process, and a user changing regional settings mid-command is not a
state this layer promises to observe.

## 5. Data-source API mapping

`LocaleValues` fields and the exact Win32 source. `LOCALE_*` constants are
`LCTYPE` (`DWORD`) values passed to `GetLocaleInfoEx`; `+N` denotes an ordinal
range walked in a loop.

| POSIX item | Win32 LCType | transform |
| --- | --- | --- |
| `charmap` (suffix `.UTF-8`) | — (POSIX spelling) | `UTF-8` |
| `charmap` (no suffix) | `LOCALE_IDEFAULTANSICODEPAGE` → `GetCPInfo` | codepage → charmap name table (§7) |
| `decimal_point` | `LOCALE_SDECIMAL` (0x0E) | verbatim |
| `thousands_sep` | `LOCALE_STHOUSAND` (0x0F) | verbatim |
| `grouping` | `LOCALE_SGROUPING` (0x10) | `"3;0"` → sizes `{3}`, repeat; POSIX text `3` |
| `int_curr_symbol` | `LOCALE_SINTLSYMBOL` (0x15) | `+ " "` when non-empty (ISO 4217 convention, glibc-compatible) |
| `currency_symbol` | `LOCALE_SCURRENCY` (0x14) | verbatim |
| `mon_decimal_point` | `LOCALE_SMONDECIMALSEP` (0x16) | verbatim |
| `mon_thousands_sep` | `LOCALE_SMONTHOUSANDSEP` (0x17) | verbatim |
| `mon_grouping` | `LOCALE_SMONGROUPING` (0x18) | as `grouping` |
| `positive_sign` | `LOCALE_SPOSITIVESIGN` (0x50) | verbatim |
| `negative_sign` | `LOCALE_SNEGATIVESIGN` (0x51) | verbatim |
| `frac_digits` | `LOCALE_ICURRDIGITS` (0x19) | decimal → int |
| `int_frac_digits` | `LOCALE_IINTLCURRDIGITS` (0x1A) | decimal → int |
| `p_cs_precedes` | `LOCALE_ICURRENCY` (0x1B) | 0/2 → 1, 1/3 → 0 |
| `p_sep_by_space` | `LOCALE_ICURRENCY` (0x1B) | 2/3 → 1, else 0 |
| `n_cs_precedes` | `LOCALE_INEGCURR` (0x1C) | table §8 |
| `n_sep_by_space` | `LOCALE_INEGCURR` (0x1C) | table §8 |
| `p_sign_posn` | derived | 1 when sign/currency data present, else -1 |
| `n_sign_posn` | `LOCALE_INEGCURR` (0x1C) | table §8 |
| `abday[0..6]` | `LOCALE_SABBREVDAYNAME7,1..6` (0x37,0x31..0x36) | Monday-first → Sunday-first |
| `day[0..6]` | `LOCALE_SDAYNAME7,1..6` (0x30,0x2A..0x2F) | Monday-first → Sunday-first |
| `abmon[0..11]` | `LOCALE_SABBREVMONTHNAME1+0..11` (0x44..0x4F) | verbatim |
| `mon[0..11]` | `LOCALE_SMONTHNAME1+0..11` (0x38..0x43) | verbatim |
| `am_pm` | `LOCALE_SAM`/`LOCALE_S1159` (0x28), `LOCALE_SPM`/`LOCALE_S2359` (0x29) | `am + ";" + pm` (empty → `;`, glibc de_DE shape) |
| `d_fmt` | `LOCALE_SSHORTDATE` (0x1F) | picture → strftime (§9) |
| `t_fmt` | `LOCALE_STIMEFORMAT` (0x1003) | picture → strftime (§9) |
| `t_fmt_ampm` | `LOCALE_STIMEFORMAT` + `LOCALE_SAM/SPM` | `%I:%M:%S %p` when 12-hour picture and AM/PM non-empty, else `""` |
| `d_t_fmt` | synthesized | C record: glibc `"%a %b %e %H:%M:%S %Y"`; other: `d_fmt + " " + t_fmt` (§9) |
| `era` | — | always empty (no Win32 era data) |
| `yesexpr`/`noexpr` | — | C value (`^[yY]`/`^[nN]`), §10 |
| `yesstr`/`nostr` | — | empty (C value) |
| resolution probe | `LOCALE_SISO639LANGNAME` (0x59) | presence decides `resolved`; empty failure → C record |
| ctype classification | `GetStringTypeW(CT_CTYPE1)` | C1_* bit mask → POSIX classes (§10) |

Deliberately **not** used:

- `GetDynamicTimeZoneInformation` — the Windows TZ database answers "what is
  this machine's zone called", not POSIX `TZ` rule strings; `tzset(1)`
  (`src/commands/tzset.cpp`) already owns that face. A locale database that
  mixed them would make `TZ=` handling ambiguous.
- `setlocale()`/`localeconv()` from the CRT — the CRT answers for the CRT's
  active locale, which is process state, not a *value model*, and it cannot
  answer for a locale other than the active one. Using it would re-introduce
  the "one global value" limitation this issue removes.

## 6. Name resolution, environment precedence, fallback

```
name_for_category(cat):
  LC_ALL (if non-empty) → LC_<cat> (if non-empty) → LANG (if non-empty)
  → Windows user default (GetUserDefaultLocaleName), POSIX spelling
  → "C"
```

- `LC_ALL` wins for every category (POSIX).
- The Windows user default is the *last* fallback, not the first: on a Windows
  host with no POSIX locale environment (the normal case) it is the only
  source, which keeps WinuxCmd's documented "Windows-native default"
  (audit-locale.md, platform faces).
- POSIX spellings are normalized for lookup only: strip `@modifier`, split
  `.codeset`, translate `_` → `-` for the Win32 call. `C`, `POSIX` and `""`
  resolve to the synthetic C record. `C.UTF-8`/`C.utf8` resolve to the C
  record with `codeset = UTF-8` (glibc's C.UTF-8 is C values + UTF-8).
- Windows user overrides (`LOCALE_NOUSEROVERRIDE` is *not* passed) are
  honoured for the user's own locale: this layer reports the machine the
  way Windows formats it, and the tests pin `en_US` (default NLS data) so
  they do not depend on a customized host locale.
- Failure fallback is **C locale semantics**, never the host locale:
  `GetLocaleInfoEx` returning 0 for a field yields the C record's value for
  that field (empty string / -1), and an unresolvable name marks
  `resolved = false` while still returning a usable C-based record. Commands
  therefore never print a mix of two locales.
- Unlike `i18n::system_locale()` (§11), this layer does **not** read
  `WINUX_LANG`: the message-catalog locale and the POSIX value locale are
  different namespaces.

## 7. Codeset model

`Codeset { std::string charmap; unsigned codepage; unsigned max_char_size;
bool utf8; bool dbcs; }`

1. A codeset in the POSIX spelling (`.UTF-8`, `.utf8`, `.UTF8`) is authoritative
   → `charmap = "UTF-8"`, `codepage = 65001`, `max_char_size = 4`.
2. Otherwise `LOCALE_IDEFAULTANSICODEPAGE` + `GetCPInfo(cp)`:
   `charmap` from a fixed glibc-name table (ASCII 20127 → `ANSI_X3.4-1968`,
   65001 → `UTF-8`, 125x → `CP125x`, 936 → `GBK`, 950 → `BIG5`,
   932 → `SHIFT_JIS`, 949 → `EUC-KR`, 874 → `CP874`, 437/850/852/866 →
   `IBMxxx`, 2859x → `ISO-8859-x`, 10000 → `MACINTOSH`, …), else `"CP<cp>"`.
   `max_char_size` and the lead-byte ranges come from `GetCPInfo`.
3. C/POSIX → `ANSI_X3.4-1968`, codepage 20127, `max_char_size = 1`.

`GetCPInfo` failure keeps `codepage` and reports `"CP<cp>"`; the value model
degrades to "unknown single-byte" rather than lying about UTF-8.

## 8. Monetary projection

`LOCALE_ICURRENCY` (positive format):

| value | Windows | p_cs_precedes | p_sep_by_space |
| --- | --- | --- | --- |
| 0 | `$1` | 1 | 0 |
| 1 | `1$` | 0 | 0 |
| 2 | `$ 1` | 1 | 1 |
| 3 | `1 $` | 0 | 1 |

`LOCALE_INEGCURR` (negative format; glibc `lconv` has no single field, so the
three POSIX fields come from one):

| value | Windows | n_cs_precedes | n_sep_by_space | n_sign_posn |
| --- | --- | --- | --- | --- |
| 0 | `($1)` | 1 | 0 | 0 |
| 1 | `-$1` | 1 | 0 | 1 |
| 2 | `$-1` | 1 | 0 | 3 |
| 3 | `$1-` | 1 | 0 | 4 |
| 4 | `(1$)` | 0 | 0 | 0 |
| 5 | `-1$` | 0 | 0 | 1 |
| 6 | `1-$` | 0 | 0 | 4 |
| 7 | `1$-` | 0 | 0 | 2 |
| 8 | `-1 $` | 0 | 1 | 1 |
| 9 | `-$ 1` | 1 | 1 | 1 |
| 10 | `$ 1-` | 1 | 1 | 2 |
| 11 | `1 $-` | 0 | 1 | 2 |
| 12 | `$ -1` | 1 | 1 | 3 |
| 13 | `1- $` | 0 | 1 | 4 |
| 14 | `($ 1)` | 1 | 1 | 0 |
| 15 | `(1 $)` | 0 | 1 | 0 |

Out-of-range values fall back to `-1` (unset), matching the C record.
`p_sign_posn = 1` only when the Windows record carries currency data
(`currency_symbol` or `int_curr_symbol` non-empty); otherwise `-1`, which is
what glibc's C locale reports.

Grouping: `LOCALE_SGROUPING` is a `;`-separated run of group sizes where a
trailing `0` means "repeat the previous size". The POSIX `lconv` form is a
byte string of sizes terminated by `CHAR_MAX` for "repeat". `locale(1)`
renders it as glibc does in `-k` mode: `-1` when there is no grouping, else
the sizes joined with `;` (`3`, `3;2`). Values that never occur on Windows
(`3;2;0`) are still parsed so the model is not shaped around en-US.

## 9. LC_TIME projection

Day/month names: Win32 `LOCALE_SDAYNAME1..7` is Monday-first; POSIX `day[0]`
is Sunday, so the order is `{7,1,2,3,4,5,6}`. Months already start at January.

`am_pm` is `S1159 + ";" + S2359`; de-DE gives `";"` for two empty strings,
which is byte-identical to glibc's de_DE value.

Date/time pictures (`LOCALE_SSHORTDATE`, `LOCALE_STIMEFORMAT`,
`LOCALE_SDURATION`) are Windows pattern strings, not `strftime`. The
translator walks UTF-16 runs:

| picture | strftime | note |
| --- | --- | --- |
| `d`, `dd` | `%d`, `%d` | Windows `d` is unpadded; POSIX has no portable unpadded day, so both map to `%d` (glibc's own d_fmt uses `%d` in zh_CN) |
| `ddd` | `%a` | |
| `dddd` | `%A` | |
| `M`, `MM` | `%m`, `%m` | same padding decision as `d` |
| `MMM` | `%b` | |
| `MMMM` | `%B` | |
| `y`, `yy` | `%y`, `%y` | |
| `yyy`, `yyyy` | `%Y` | |
| `h`, `hh` | `%I`, `%I` | 12-hour |
| `H`, `HH` | `%H`, `%H` | 24-hour |
| `m`, `mm` | `%M` | |
| `s`, `ss` | `%S` | |
| `t`, `tt` | `%p` | |
| `g`, `gg` | dropped | era has no POSIX `strftime` token |
| `'…'` | literal | quotes removed, `%` escaped |
| other | literal | `%` escaped as `%%` |

`t_fmt_ampm`: `"%I:%M:%S %p"` when the picture uses `h`/`tt` and either
meridiem string is non-empty, else `""`. That reproduces glibc's split
between en_US (`%I:%M:%S %p`) and de_DE (`""`), and C (`%I:%M:%S %p`).

`d_t_fmt`: glibc stores the composite per locale; Windows has no equivalent.
The C record keeps glibc's exact `"%a %b %e %H:%M:%S %Y"`. Other locales
synthesize `d_fmt + " " + t_fmt` — a documented simulation choice, not a
translation of glibc's locale files (e.g. glibc zh_CN uses
`"%Y年%m月%d日 %A %H时%M分%S秒"`, while the Windows zh-CN database yields
`"%Y/%m/%d %H:%M:%S"`). This difference is a *data-source* difference, not a
bug: the layer's contract is "Windows NLS values projected onto POSIX
semantics".

## 10. LC_CTYPE classification

`GetStringTypeW(CT_CTYPE1, …)` returns `C1_UPPER/LOWER/DIGIT/SPACE/PUNCT/
CNTRL/BLANK/XDIGIT/ALPHA`. The layer caches a 128-entry `uint16_t` ASCII table
built once with that API; ASCII is locale-invariant, so the table can be
verified by `static_assert` against hard-coded expectations at compile time
(no runtime probe needed). Classification above 0x7F goes to `GetStringTypeW`
per call (BMP units; surrogate pairs are classified per unit and documented as
a limitation for astral scripts).

The classification API is exported but has **no consumer yet**: no command in
the tree exposes POSIX character classes through a locale (the regex engine
owns its own classes). It is implemented so that `tr(1)`/`grep` character
classes can later follow the locale instead of re-deriving ASCII tables. The
ASCII table is compile-time asserted (16 `static_assert`s), so that half is
verified by the build; the `GetStringTypeW` path above 0x7F has no runtime
consumer this round and is therefore **unverified** — treat it as the API
contract for the follow-up rather than as tested behaviour.

## 11. Relationship to `src/utils/i18n.cppm`

Two different "locale" concepts, deliberately kept apart:

| | `i18n.cppm` | `locale_db.cppm` |
| --- | --- | --- |
| question | which *message catalogue* translates UI text | which *value database* formats numbers/dates/currency |
| selector | `WINUX_LANG` first, then `LC_ALL`/`LC_MESSAGES`/`LANG` | `LC_ALL`/`LC_<cat>`/`LANG`, then Windows user default |
| fallback | English source text | C-locale semantics |
| keys | stable `command.*`/`common.*` keys, `legacy.<FNV>` hashes | none (no translatable text) |
| cost guard | 256-byte gate in `translate_legacy` (a legacy key can never be longer than the longest extracted literal) | none needed (no lookup) |

The 256-byte gate exists because `translate_legacy` hashes arbitrary runtime
text; `locale_db` does not translate text at all, so the gate is irrelevant
there. The only shared concern is the *environment precedence shape*: i18n
deliberately lets `WINUX_LANG` override the POSIX locale (issue #1155) while
`locale_db` ignores `WINUX_LANG`. That asymmetry is documented here so a
future "unify the locale plumbing" patch does not break one of the two.

New user-visible strings introduced by this change: none. The locale and date
applets keep their existing message keys; the removed literals
(`^[yY]`, `USD `, `$`, …) stop being extracted into the English catalogue,
which shrinks the i18n drift ratchet (issue #1549 already tracks the orphan
`legacy.*` keys on the catalogue side).

## 13. Remaining work

1. `-a`/`-m` inventories from the Windows NLS catalogue
   (`EnumSystemLocalesEx`, `GetLocaleInfoEx(LOCALE_SLIST)`/codepage probes)
   instead of the current fixed representative lists.
2. Per-category raw dumps (`locale LC_CTYPE`, `locale -c LC_TIME`): glibc
   emits a value-only item stream including the full `ctype` class tables
   (`upper`/`lower`/… character lists) and eraless `cal_direction`/
   `first_weekday` fields. That needs the codeset's character table, not just
   the API values; the CTYPE dump in particular cannot be faked.
3. `yesstr`/`nostr`/`yesexpr`/`noexpr`: no Win32 counterpart (verified: no
   `LOCALE_SYES`/`LOCALE_SNO` in `winnls.h`). Today they keep the C values.
   A future source could be a bundled CLDR slice; until then the C answers are
   the honest ones.
4. `int_p_cs_precedes`/`int_p_sep_by_space`/`int_n_*`/`int_*_sign_posn`: Win32
   has one monetary format per locale, no separate international form, so
   these stay unavailable (glibc answers them from its own locale files).
5. LC_PAPER/NAME/ADDRESS/TELEPHONE/MEASUREMENT/IDENTIFICATION items: Win32
   exposes country/language names (`LOCALE_SISO3166CTRYNAME2`,
   `LOCALE_SNATIVECOUNTRYNAME`, `LOCALE_IMEASURE`) but no postal/telephone
   *format* strings. Answer only what the API can back.
6. `date_fmt` (glibc's `%a %b %e %H:%M:%S %Z %Y` variant) and `era_*`.
7. Wire `locale_db` into the numeric consumers (`numfmt`, `printf`'s `'`
   flag, `sort -n`) once their Rust/C++ ownership is settled; this round only
   proves the model through `locale`/`date`.
8. i18n repository sync: the removed literal requires dropping
   `legacy.f2cddbed2ebac47b` (`"LC_ALL="`) from
   `unixwin/winuxcmd-i18n/catalogs/zh-CN/catalog.json` plus the mandatory
   `VERSION` bump (AGENTS.md). The baseline record in this repository
   (`scripts/i18n-drift-baseline.json`) carries the key until that sync
   lands. Not done in this worktree: the lane is not allowed to commit or
   push to either repository.
