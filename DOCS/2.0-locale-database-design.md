# 2.0 — locale-database simulation layer (design)

Status: phase 1 (value model) and phase 2 (inventories, category dumps,
international monetary/date/week items, >0x7F ctype verification) implemented;
tracked by issue #1549 (parent #1488). Supersedes the `keyword_value()` lookup
table in `src/commands/locale.cpp`.

## 1. Problem

`locale(1)` answered every NAME operand from a hard-coded table in
`src/commands/locale.cpp` (`keyword_value()`, 25 keywords). Every value was a
C-locale/en-US hybrid: `int_curr_symbol` = `USD `, `currency_symbol` = `$`,
`frac_digits` = `1`, `yesstr` = `yes`, `day`/`mon` English, `charmap` from a
two-branch environment probe. Consequences measured against glibc 2.39:

```
# glibc C locale          # WinuxCmd before this change
frac_digits=-1            frac_digits=1
currency_symbol=""        currency_symbol="$"
yesstr=""                 yesstr="yes"
decimal_point="."         decimal_point="."      (agrees by accident)
```

and `date +%x/%X/%c` always used the C-locale forms, regardless of the locale
the environment selected (or the Windows user locale). There is no notion of a
*locale database*: each keyword was a literal, so `-a`/`-m` inventories,
per-category dumps and any locale other than C could only ever be special-cased.

## 2. Scope

In scope (phase 1 + phase 2, issue #1549):

- LC_CTYPE codeset: `charmap` (and the underlying codeset model), plus the
  glibc category dump (`locale LC_CTYPE`, `-c`, `-k`) and the runtime
  verification of the `>0x7F` classification path.
- LC_NUMERIC: `decimal_point`, `thousands_sep`, `grouping`, the `*-wc`
  separator values and `numeric-codeset`.
- LC_MONETARY: all POSIX `lconv` monetary fields exposed by glibc `locale -k`,
  including the six international (`int_*`) fields, `crncystr` and the
  financial `duo_*`/`uno_*` block.
- LC_TIME: `day`/`abday`/`mon`/`abmon`/`am_pm`/`d_fmt`/`t_fmt`/`d_t_fmt`/
  `t_fmt_ampm`/`date_fmt`, `week-*`/`first_weekday`/`first_workday`/
  `cal_direction`, `alt_mon`/`ab_alt_mon`, consumed by `date` for the default
  format and `%a %A %b %h %B %p %P %r %x %X %c`.
- `locale -a` from `EnumSystemLocalesEx(LOCALE_ALL)` and `locale -m` from
  `EnumSystemCodePagesW(CP_SUPPORTED)`.
- glibc-shaped category dumps for all twelve categories
  (`locale CATEGORY`, `locale -c CATEGORY`, `locale -k CATEGORY`), driven by
  the categories.def item order.
- C/POSIX synthesis (exact glibc C-locale values) and failure fallback.
- Per-category environment resolution: `LC_ALL` > `LC_<CATEGORY>` > `LANG` >
  Windows user default.

Out of scope (documented remaining work, §14): values for
LC_PAPER/NAME/ADDRESS/TELEPHONE/IDENTIFICATION items beyond the C constant
block, collation (`LC_COLLATE` rules), `yesstr`/`nostr` (no Win32 data source),
message translation (`WINUX_LANG`, owned by `src/utils/i18n.cppm`).

## 4. Architecture

```
        POSIX spelling                      Win32 NLS                      POSIX projection
  ┌──────────────────────┐          ┌────────────────────────┐        ┌──────────────────────────┐
  │ LC_ALL/LC_TIME/LANG  │          │ GetLocaleInfoEx(W)     │        │ lconv-shaped Numeric /    │
  │ "zh_CN.UTF-8@mod"    │─resolve─▶│ LOCALE_S*/LOCALE_I*    │──────▶ │ Monetary, strftime-shaped │
  │ "C", "POSIX", ""     │  name    │ GetCPInfo              │        │ Time, Codeset, ctype bits │
  └──────────────────────┘          │ GetUserDefaultLocaleName│       └───────────┬──────────────┘
                                    │ GetStringTypeW         │                    │
                                    └────────────────────────┘                    ▼
                                                                    locale(1)  date(1)  [future]
```

Three stages, each independently testable:

1. **Name resolution** turns the POSIX spelling into either the synthetic C
   locale or a Windows BCP-47 name. Never silently substitutes a different
   locale: a name that does not resolve is reported by lookup failing into the
   C record and the caller keeps the requested spelling in `LocaleValues::name`
   (`resolved=false`).
2. **Data acquisition** is the only place that calls Win32. Every field is
   read through one helper that handles the two-call size protocol, `0`
   returns, and number/string distinction.
3. **Projection** converts Win32 shapes into POSIX semantics: `INEGCURR`
   format code → `n_cs_precedes`/`n_sep_by_space`/`n_sign_posn`; `SGROUPING`
   `"3;0"` → POSIX grouping bytes; Windows date/time pictures → `strftime`
   patterns; day-of-week Monday-first → POSIX Sunday-first.

`module utils:locale_db` (`src/utils/locale_db.cppm`) exports the value types
and the cache; it has no output, no I18N text and no process state beyond the
immutable cache. Consumers (`locale.cpp`, `date.cpp`) own rendering.

Cache: one `unordered_map<canonical POSIX name, LocaleValues>` guarded by a
mutex, filled lazily and never erased. The record is built *outside* the lock
(duplicate work on a race is harmless; `emplace` keeps the first), and
references returned by `lookup()` stay valid for the process lifetime because
node-based rehashing does not invalidate them. The key is the canonicalized
spelling including the codeset (`en_US.UTF-8` and `en_US` are different
records; `zh-CN` and `zh_CN` are the same), so a command that asks for the
same locale per `strftime` specifier pays one Win32 round-trip per field for
the whole process — `date` formats with a cached record, not per call. There
is no TTL and no invalidation: the NLS database does not change under a
running process, and a user changing regional settings mid-command is not a
state this layer promises to observe.

Deliberately **not** used:

- `GetDynamicTimeZoneInformation` — the Windows TZ database answers "what is
  this machine's zone called", not POSIX `TZ` rule strings; `tzset(1)`
  (`src/commands/tzset.cpp`) already owns that face. A locale database that
  mixed them would make `TZ=` handling ambiguous.
- `setlocale()`/`localeconv()` from the CRT — the CRT answers for the CRT's
  active locale, which is process state, not a *value model*, and it cannot
  answer for a locale other than the active one. Using it would re-introduce
  the "one global value" limitation this issue removes.

## 6. Name resolution, environment precedence, fallback

```
name_for_category(cat):
  LC_ALL (if non-empty) → LC_<cat> (if non-empty) → LANG (if non-empty)
  → Windows user default (GetUserDefaultLocaleName), POSIX spelling
  → "C"
```

- `LC_ALL` wins for every category (POSIX).
- The Windows user default is the *last* fallback, not the first: on a Windows
  host with no POSIX locale environment (the normal case) it is the only
  source, which keeps WinuxCmd's documented "Windows-native default"
  (audit-locale.md, platform faces).
- POSIX spellings are normalized for lookup only: strip `@modifier`, split
  `.codeset`, translate `_` → `-` for the Win32 call. `C`, `POSIX` and `""`
  resolve to the synthetic C record. `C.UTF-8`/`C.utf8` resolve to the C
  record with `codeset = UTF-8` (glibc's C.UTF-8 is C values + UTF-8).
- Windows user overrides (`LOCALE_NOUSEROVERRIDE` is *not* passed) are
  honoured for the user's own locale: this layer reports the machine the
  way Windows formats it, and the tests pin `en_US` (default NLS data) so
  they do not depend on a customized host locale.
- Failure fallback is **C locale semantics**, never the host locale:
  `GetLocaleInfoEx` returning 0 for a field yields the C record's value for
  that field (empty string / -1), and an unresolvable name marks
  `resolved = false` while still returning a usable C-based record. Commands
  therefore never print a mix of two locales.
- Unlike `i18n::system_locale()` (§12), this layer does **not** read
  `WINUX_LANG`: the message-catalog locale and the POSIX value locale are
  different namespaces.

## 7. Codeset model

`Codeset { std::string charmap; unsigned codepage; unsigned max_char_size;
bool utf8; bool dbcs; }`

1. A codeset in the POSIX spelling (`.UTF-8`, `.utf8`, `.UTF8`) is authoritative
   → `charmap = "UTF-8"`, `codepage = 65001`, `max_char_size = 4`.
2. Otherwise `LOCALE_IDEFAULTANSICODEPAGE` + `GetCPInfo(cp)`:
   `charmap` from a fixed glibc-name table (ASCII 20127 → `ANSI_X3.4-1968`,
   65001 → `UTF-8`, 125x → `CP125x`, 936 → `GBK`, 950 → `BIG5`,
   932 → `SHIFT_JIS`, 949 → `EUC-KR`, 874 → `CP874`, 437/850/852/866 →
   `IBMxxx`, 2859x → `ISO-8859-x`, 10000 → `MACINTOSH`, …), else `"CP<cp>"`.
   `max_char_size` and the lead-byte ranges come from `GetCPInfo`.
3. C/POSIX → `ANSI_X3.4-1968`, codepage 20127, `max_char_size = 1`.

`GetCPInfo` failure keeps `codepage` and reports `"CP<cp>"`; the value model
degrades to "unknown single-byte" rather than lying about UTF-8.

## 8. Monetary projection

`LOCALE_ICURRENCY` (positive format):

| value | Windows | p_cs_precedes | p_sep_by_space |
| --- | --- | --- | --- |
| 0 | `$1` | 1 | 0 |
| 1 | `1$` | 0 | 0 |
| 2 | `$ 1` | 1 | 1 |
| 3 | `1 $` | 0 | 1 |

`LOCALE_INEGCURR` (negative format; glibc `lconv` has no single field, so the
three POSIX fields come from one):

| value | Windows | n_cs_precedes | n_sep_by_space | n_sign_posn |
| --- | --- | --- | --- | --- |
| 0 | `($1)` | 1 | 0 | 0 |
| 1 | `-$1` | 1 | 0 | 1 |
| 2 | `$-1` | 1 | 0 | 3 |
| 3 | `$1-` | 1 | 0 | 4 |
| 4 | `(1$)` | 0 | 0 | 0 |
| 5 | `-1$` | 0 | 0 | 1 |
| 6 | `1-$` | 0 | 0 | 4 |
| 7 | `1$-` | 0 | 0 | 2 |
| 8 | `-1 $` | 0 | 1 | 1 |
| 9 | `-$ 1` | 1 | 1 | 1 |
| 10 | `$ 1-` | 1 | 1 | 2 |
| 11 | `1 $-` | 0 | 1 | 2 |
| 12 | `$ -1` | 1 | 1 | 3 |
| 13 | `1- $` | 0 | 1 | 4 |
| 14 | `($ 1)` | 1 | 1 | 0 |
| 15 | `(1 $)` | 0 | 1 | 0 |

Out-of-range values fall back to `-1` (unset), matching the C record.
`p_sign_posn = 1` only when the Windows record carries currency data
(`currency_symbol` or `int_curr_symbol` non-empty); otherwise `-1`, which is
what glibc's C locale reports.

### 8.1 International format (`int_*`) and the financial block

POSIX carries a second currency format (`int_p_cs_precedes`,
`int_p_sep_by_space`, `int_n_cs_precedes`, `int_n_sep_by_space`,
`int_p_sign_posn`, `int_n_sign_posn`) next to the local one. Windows has a
single monetary format per locale: `LOCALE_ICURRENCY`/`LOCALE_INEGCURR`
describe the local layout, and `LOCALE_SINTLSYMBOL` names the ISO 4217 symbol
but says nothing about where the symbol or sign goes. The layer therefore
reports the C value `-1` for all six fields, for every locale, rather than
guessing from the local format. Measured against glibc this is the honest
answer: en-US glibc reports `1/1/1/1/1/1`, de-DE `0/1/0/1/1/1`, zh-CN
`1/0/1/0/1/1`, while Windows carries no field that distinguishes them.

`crncystr` (`nl_langinfo(CRNCYSTR)`) is derived instead: the sign-position
marker (`-` when the local format puts the symbol first, `+` when it follows)
concatenated with `currency_symbol` — `-$` for en-US, `+€` for de-DE, `-` for
C (which has no symbol), byte-identical to glibc.

The financial (`duo_*`) block mirrors the primary fields, which is what every
glibc stock locale file does. `uno_valid_from`/`uno_valid_to`/
`duo_valid_from`/`duo_valid_to`/`conversion_rate` keep glibc's
"no dual-currency" defaults (`10101`, `99991231`, `1;1`); Windows has no
financial-currency item.

Grouping: `LOCALE_SGROUPING` is a `;`-separated run of group sizes where a
trailing `0` means "repeat the previous size". The POSIX `lconv` form is a
byte string of sizes terminated by `CHAR_MAX` for "repeat". `locale(1)`
renders it as glibc does in `-k` mode: `-1` when there is no grouping, else
the sizes joined with `;` (`3`, `3;2`). Values that never occur on Windows
(`3;2;0`) are still parsed so the model is not shaped around en-US.

## 9. LC_TIME projection

Day/month names: Win32 `LOCALE_SDAYNAME1..7` is Monday-first; POSIX `day[0]`
is Sunday, so the order is `{7,1,2,3,4,5,6}`. Months already start at January.

`am_pm` is `S1159 + ";" + S2359`; de-DE gives `";"` for two empty strings,
which is byte-identical to glibc's de_DE value.

Date/time pictures (`LOCALE_SSHORTDATE`, `LOCALE_STIMEFORMAT`,
`LOCALE_SDURATION`) are Windows pattern strings, not `strftime`. The
translator walks UTF-16 runs:

| picture | strftime | note |
| --- | --- | --- |
| `d`, `dd` | `%d`, `%d` | Windows `d` is unpadded; POSIX has no portable unpadded day, so both map to `%d` (glibc's own d_fmt uses `%d` in zh_CN) |
| `ddd` | `%a` | |
| `dddd` | `%A` | |
| `M`, `MM` | `%m`, `%m` | same padding decision as `d` |
| `MMM` | `%b` | |
| `MMMM` | `%B` | |
| `y`, `yy` | `%y`, `%y` | |
| `yyy`, `yyyy` | `%Y` | |
| `h`, `hh` | `%I`, `%I` | 12-hour |
| `H`, `HH` | `%H`, `%H` | 24-hour |
| `m`, `mm` | `%M` | |
| `s`, `ss` | `%S` | |
| `t`, `tt` | `%p` | |
| `g`, `gg` | dropped | era has no POSIX `strftime` token |
| `'…'` | literal | quotes removed, `%` escaped |
| other | literal | `%` escaped as `%%` |

`t_fmt_ampm`: `"%I:%M:%S %p"` when the picture uses `h`/`tt` and either
meridiem string is non-empty, else `""`. That reproduces glibc's split
between en_US (`%I:%M:%S %p`) and de_DE (`""`), and C (`%I:%M:%S %p`).

`d_t_fmt`: glibc stores the composite per locale; Windows has no equivalent.
The C record keeps glibc's exact `"%a %b %e %H:%M:%S %Y"`. Other locales
synthesize `d_fmt + " " + t_fmt` — a documented simulation choice, not a
translation of glibc's locale files (e.g. glibc zh_CN uses
`"%Y年%m月%d日 %A %H时%M分%S秒"`, while the Windows zh-CN database yields
`"%Y/%m/%d %H:%M:%S"`). This difference is a *data-source* difference, not a
bug: the layer's contract is "Windows NLS values projected onto POSIX
semantics".

`date_fmt` (glibc's `DATE_FMT`, the default `date` output): Windows has no
item. The C record keeps glibc's exact `"%a %b %e %H:%M:%S %Z %Y"`; a resolved
record uses `d_t_fmt + " %Z"`. `date(1)` now formats its default output from
this field, so C/POSIX stays byte-identical while other locales stop ignoring
the selected locale (the projection differs from glibc's locale-file pattern,
recorded in §13).

Week data:

| item | source | projection |
| --- | --- | --- |
| `week-ndays` | — | `7` |
| `week-1stday` | — | `19971130` (glibc's reference Sunday) |
| `week-1stweek` | `LOCALE_IFIRSTWEEKOFYEAR` | `2` → `4` (ISO-style first full week), anything else → `1` |
| `first_weekday` | `LOCALE_IFIRSTDAYOFWEEK` | Windows 0=Monday..6=Sunday → glibc 2..7,1 |
| `first_workday` | — | `2` (Monday); Windows exposes no work-week item |
| `cal_direction` | — | `1` |
| `timezone` | — | empty (POSIX `TZ` rule strings are `tzset(1)`'s face) |
| `alt_mon`/`ab_alt_mon` | — | `mon`/`abmon` |

The projections were checked against glibc for C, en_US, de_DE and zh_CN:
`first_weekday` and `week-1stweek` agree for all four; `first_workday` is a
constant because the NLS API has no equivalent.

## 10. LC_CTYPE classification

`GetStringTypeW(CT_CTYPE1, …)` returns `C1_UPPER/LOWER/DIGIT/SPACE/PUNCT/
CNTRL/BLANK/XDIGIT/ALPHA/DEFINED`. ASCII is locale-invariant, so the layer
uses a 128-entry table pinned by `static_assert`s; classification above 0x7F
goes to `GetStringTypeW` per call (BMP units; surrogate pairs report 0).

Phase 2 gave that path its first runtime caller: `locale-ctype-check`
(`tests/tools/locale_ctype_check.cpp`, built as a top-level target and
registered with CTest as `locale-ctype-runtime`). Measured on Windows 11 NLS:

| code point | CT_CTYPE1 bits | POSIX classes |
| --- | --- | --- |
| U+00E9 é | `LOWER|ALPHA|DEFINED` | lower, alpha, alnum, graph, print |
| U+00C9 É | `UPPER|ALPHA|DEFINED` | upper, alpha, alnum, graph, print |
| U+4E2D 中 | `ALPHA|DEFINED` | alpha, alnum, graph, print |
| U+0661 ١ | `DIGIT|DEFINED` | digit, alnum, graph, print |
| U+3000 (ideographic space) | `SPACE|BLANK|DEFINED` | space, blank, print |
| U+00A5 ¥ | `PUNCT|DEFINED` | punct, graph, print |
| U+FF10 ０ | `DIGIT|XDIGIT|DEFINED` | digit, xdigit, graph, print |
| U+FF21 Ａ | `UPPER|ALPHA|XDIGIT|DEFINED` | upper, alpha, graph, print |
| U+0410 А / U+0430 а | `UPPER|ALPHA` / `LOWER|ALPHA` | upper/lower + alpha |
| U+20AC € | `DEFINED` only | *no* POSIX class |
| U+0301 combining acute | `DEFINED` only | *no* POSIX class |
| U+1D400 (astral) | — | 0 (UTF-16 units only) |

`C1_DEFINED` is not a POSIX class and is dropped. The consequence is a real
limitation of the data source, not of the projection: currency symbols,
combining marks and other characters that Windows marks only `C1_DEFINED`
report no class, while the ASCII table synthesizes `punct` for symbols such
as `$`. Glibc's UTF-8 locales would call `€` printable. The check pins the
behaviour so a future source (ICU/CLDR or a bundled table) changes it
deliberately.

The classification API still has no command consumer (the regex engine owns
its own classes); it is the API contract for a future `tr(1)`/`grep`
migration.

## 11. Inventories and category dumps

### 11.1 `locale -a`

The list is the Windows NLS catalogue, not a fixed representative set:

1. `C`, `C.utf8`, `POSIX` are always present (POSIX requires C/POSIX; C.utf8
   is the codeset the layer also synthesizes).
2. `EnumSystemLocalesEx(LOCALE_ALL)` yields the Windows names (`en-US`,
   `zh-CN`, `az-Cyrl-AZ`, …). Each name is projected to POSIX spelling
   (`-` → `_`) and gets a codeset suffix built from its
   `LOCALE_IDEFAULTANSICODEPAGE`: `en_US.cp1252`, `zh_CN.gbk`,
   `ja_JP.shift_jis`, `de_DE.cp1252`. The suffix is normalized the way glibc's
   locale archive normalizes codesets: lowercase, alphanumerics only
   (`UTF-8` → `utf8`, `ISO-8859-1` → `iso88591`).
3. Windows sort-order variants (`de-DE_phoneb`, `zh-CN_stroke`) contain a `_`
   that is not a separator in POSIX spelling; they are skipped because
   `lookup()` cannot round-trip them.
4. A byte-sorted `std::set` supplies both sorting and de-duplication. glibc
   sorts with `tsearch` + `strcoll` of the *active collation* and also folds
   in `locale.alias` names (e.g. `catalan`); this layer has no collation or
   alias-file model, so it always sorts under C and lists real locale names
   only. Under `LC_ALL=C` the result is byte-identical to glibc's ordering
   rule.

Measured on the development host: 859 lines (3 + 856 Windows names) versus
glibc's 5 installed locales. The count difference is the platform face: the
NLS database knows every locale Windows can format, glibc knows what
`localedef` installed. Entries whose locale reports no ANSI code page (many
neutral two-letter names such as `aa`) get the ASCII codeset
(`aa.ansix341968`), which is the code page fallback documented in §7.

### 11.2 `locale -m`

`EnumSystemCodePagesW(CP_SUPPORTED)` supplies the installed/supported code
pages; each is named through the §7 charmap table (`CP1252`, `GBK`,
`BIG5`, `SHIFT_JIS`, …) or `CP<number>` when no glibc name is known. UTF-8 and
ANSI_X3.4-1968 are always included because the codeset model always answers
them. The result is sorted and de-duplicated bytewise. Measured: 139
charmaps on the development host versus glibc's 236 (the glibc list includes
every `charmaps/` file and its aliases; the NLS list is the code pages the
host actually ships).

`-a` wins when `-a` and `-m` are both given, matching glibc main(): the
`do_all` branch exits before the `do_charmaps` branch.

### 11.3 Category dumps (`locale CATEGORY`, `-c`, `-k`)

The item model lives in `utils:locale_db` (`category_items()`,
`item_category()`, `item_value()`), copied from glibc's `locale/categories.def`
order and limited to the item shapes `print_item()` renders (the wide-character
duplicates are skipped by glibc too, which is why `-k LC_TIME` has 28 lines,
not 45). `locale.cpp` only renders:

| mode | rendering |
| --- | --- |
| `locale CATEGORY` | raw item values, one per line |
| `locale -c CATEGORY` | category name, then the raw values |
| `locale -k CATEGORY` | `name=value` for every item |
| `locale -c NAME` (item) | the item's *category* name, then the value |
| `locale -k NAME` (item) | just that item |

`-k` follows glibc print_item(): strings and string arrays are quoted as a
whole (`day="Sun;Mon"`), string lists quote each element
(`ctype-class-names="upper";"lower"`), bytes/words/arrays stay bare. All
twelve categories are answered; `LC_ALL` is not a category (`locale LC_ALL` is
the unknown-name error, exit 1) and unknown names take the existing
`locale: unknown name "X"` path.

Value sources:

| category | source |
| --- | --- |
| LC_CTYPE | codeset model + class/map name lists; indigit/outdigit tables are the POSIX 0-9/48-57 |
| LC_NUMERIC | `Numeric` + derived `*-wc` + codeset |
| LC_TIME | `TimeFormat` (including `date_fmt`, week data, alt months) + C constants for era/alt digits/timezone |
| LC_MONETARY | `Monetary` + derived `crncystr`, mirrored `duo_*`, glibc's `uno/duo_valid_*` and `conversion_rate` defaults |
| LC_MESSAGES | `yesexpr`/`noexpr`/`yesstr`/`nostr` (C values, §14) + codeset |
| LC_MEASUREMENT | `LOCALE_IMEASURE` projected to glibc's 1/2 encoding |
| LC_COLLATE, LC_PAPER, LC_NAME, LC_ADDRESS, LC_TELEPHONE, LC_IDENTIFICATION | C constants + codeset; Windows exposes no collation rules, paper size, postal/telephone format or FDCC-set metadata (tracked in §14) |

Five LC_CTYPE items describe glibc's *compiled table layout*, not locale data:
`ctype-width`, `ctype-class-offset`, `ctype-map-offset`,
`ctype-translit-tab-size` and `ctype-translit-default-missing-len`. Windows
has no compiled ctype table to measure, so the layer reports the constants
glibc's stock tables use — `7 / 72 / 84 / 1659` for the ASCII C table,
`16 / 72 / 86 / 6398` otherwise — and the class/map name lists that go with
them (12/2 names for C, 14/3 for multibyte locales). zh_CN's extra `hanzi`
class (15 names, map offset 87) is not detected and is recorded in §13. This
is why the C/POSIX `-k LC_CTYPE` dump is byte-identical while a multibyte
locale's layout numbers are a documented simulation.

## 12. Relationship to `src/utils/i18n.cppm`

Two different "locale" concepts, deliberately kept apart:

| | `i18n.cppm` | `locale_db.cppm` |
| --- | --- | --- |
| question | which *message catalogue* translates UI text | which *value database* formats numbers/dates/currency |
| selector | `WINUX_LANG` first, then `LC_ALL`/`LC_MESSAGES`/`LANG` | `LC_ALL`/`LC_<cat>`/`LANG`, then Windows user default |
| fallback | English source text | C-locale semantics |
| keys | stable `command.*`/`common.*` keys, `legacy.<FNV>` hashes | none (no translatable text) |
| cost guard | 256-byte gate in `translate_legacy` (a legacy key can never be longer than the longest extracted literal) | none needed (no lookup) |

The 256-byte gate exists because `translate_legacy` hashes arbitrary runtime
text; `locale_db` does not translate text at all, so the gate is irrelevant
there. The only shared concern is the *environment precedence shape*: i18n
deliberately lets `WINUX_LANG` override the POSIX locale (issue #1155) while
`locale_db` ignores `WINUX_LANG`. That asymmetry is documented here so a
future "unify the locale plumbing" patch does not break one of the two.

New user-visible strings introduced by this change: none. The locale and date
applets keep their existing message keys; the removed literals
(`^[yY]`, `USD `, `$`, …) stop being extracted into the English catalogue,
which shrinks the i18n drift ratchet (issue #1549 already tracks the orphan
`legacy.*` keys on the catalogue side).

## 14. Remaining work

1. `yesstr`/`nostr`/`yesexpr`/`noexpr`: no Win32 counterpart (verified: no
   `LOCALE_SYES`/`LOCALE_SNO` in `winnls.h`). Today they keep the C values.
   A future source could be a bundled CLDR slice; until then the C answers are
   the honest ones.
2. `int_p_cs_precedes`/`int_p_sep_by_space`/`int_n_*`/`int_*_sign_posn`: Win32
   has one monetary format per locale, no separate international form, so
   these stay unavailable (`-1`) unless a CLDR/ICU source is adopted.
3. LC_PAPER/NAME/ADDRESS/TELEPHONE/IDENTIFICATION values: Win32 exposes
   country/language names (`LOCALE_SISO3166CTRYNAME2`,
   `LOCALE_SNATIVECOUNTRYNAME`, `LOCALE_IMEASURE`, already used for
   `measurement`) but no paper size, postal/telephone *format* or FDCC-set
   metadata. The dumps carry the C constant block.
4. `era`, `era_year`, `era_d_fmt`, `era_d_t_fmt`, `era_t_fmt`, `alt_digits`:
   `GetCalendarInfoEx(CAL_SERASTRING)` is calendar-scoped, not locale-scoped;
   the POSIX era shape (a `;`-joined stringlist plus alternate-format
   patterns) has no NLS counterpart. Empty/C values today.
5. Collation: `LC_COLLATE` items are C constants; wiring `strcoll` semantics
   would need a Windows collation model (`CompareStringEx`), separate from
   this value layer.
6. Multibyte LC_CTYPE fidelity: glibc's `ctype-mb-cur-max=6` for UTF-8,
   zh_CN's `hanzi` class and the per-locale class/map offsets are compiled
   locale-file facts with no NLS source; §11.3 documents the constants used.
7. `-a` nuances: Windows sort-order variants (`de-DE_phoneb`) are skipped and
   neutral locales without an ANSI code page get the ASCII suffix; a Windows
   name with `@modifier` has no POSIX projection in this layer.
8. Wire `locale_db` into the numeric consumers (`numfmt`, `printf`'s `'`
   flag, `sort -n`) once their Rust/C++ ownership is settled; this round only
   proves the model through `locale`/`date`.
9. i18n repository sync: phase 1's removed literal still requires dropping
   `legacy.f2cddbed2ebac47b` (`"LC_ALL="`) from
   `unixwin/winuxcmd-i18n/catalogs/zh-CN/catalog.json` plus the mandatory
   `VERSION` bump (AGENTS.md); phase 2 adds no key. The baseline record in
