# sed `-n /re/p` scan lane — lazy line DFA address filter (#1488)

Rebase of closed PR #1688 (`rust2/sed-scanperf`, `cc688402`) onto the unified
`winux-regex` (`CompileOptions`/`MatchCache`/dialect API). The line DFA
itself already lives on main (`crates/winux-regex/src/dfa.rs`, landed with
the grep wire); this lane wires it into sed's address selection and teaches
it the one AST shape the unified sed dialect adds.

## What changed

* `winux-regex/src/lib.rs` — `Regex::has_nfa()`: patterns without the
  Thompson NFA (back-references, an interval expansion above the NFA cap)
  are answered by the budgeted backtracker, whose exhaustion is a
  *conservative* no-match; the DFA is exact, so building it there would
  change verdicts.
* `winux-regex/src/dfa.rs` — `Node::DotRestricted` (the sed-dialect `.`,
  emitted for `strict_utf8_dot` and/or `multiline`) now builds the
  plain-dot fragment when the line model already implies its extra rules:
  `reject_invalid_utf8` is covered by the `has_dot` →
  `InputRequirement::ValidUtf8` routing, and `exclude_newline` rejects only
  `'\n'`, which is vacuous while the record `eol` is `'\n'` (every byte set
  excludes `eol`, and `eol`-containing lines never reach the DFA). A
  `sed -z ... M` `.` (eol = NUL, `'\n'` is ordinary record content) still
  declines. `M` line anchors, `` \` ``/`\'` buffer anchors and
  back-references still decline as before.
* `winux-cmds/src/sed/compile.rs` — `SedRegex` gains `dfa`/`dfa_eol` and
  `matches_line()`: the DFA answers the address boolean when
  `input_requirement()` admits the line's bytes **and** the pattern space
  contains no record delimiter byte (`N`/`G`-joined text, or `-z` NUL).
  `compile_regex` gained a `line_filter` flag: address regexes pass `true`,
  `s///` regexes pass `false` — substitutions need spans/captures and never
  build a DFA.
* `winux-cmds/src/sed/exec.rs` — `match_an_address_p` calls `matches_line`.
  Captures and match spans still come from `find_at_bytes_with`; the DFA
  only filters lines.

## Benchmarks (64 MiB corpus, best of 3, wall clock)

`python gate/sed-scanperf.py <label> <exe>` — same generator and
WSL-GNU-on-ext4 oracle as `gate/sed-bench.py`, plus an env report and the
`-n p` I/O floor. Machine: Intel Xeon w5-3433, 16C/32T, 63.7 GiB, Windows
10.0.19045, rustc 1.99.0; GNU sed 4.9 in WSL2 (kernel 6.18.33.2), input on
ext4.

| case | before | after | GNU (two runs) |
| --- | --- | --- | --- |
| `s/foo/bar/g` | 0.39 | 0.38 | 0.41–0.43 |
| `-n /lorem.*amet/p` | **0.74** | **0.28** | 0.30–0.33 |
| `y/abc/xyz/` | 0.21 | 0.20 | 1.75–1.95 |
| `s/\(a\)\(b\)/\2\1/` | 0.60 | 0.56 | 0.66–0.71 |
| `-n p` (I/O floor) | 0.21 | 0.18 | 0.16–0.18 |

`-n /re/p` is now at GNU parity (0.28 vs 0.30); nothing else moved beyond
noise. The `sed_line_probe` example isolates the selection loop on the same
input: interpreter 0.59 s (108 MB/s, ~380 ns/line) → DFA 0.14 s
(474 MB/s, ~83 ns/line), identical hit count — so most of the remaining
0.28 s is the per-line read/dispatch/print floor.

## Correctness

* `bash gate/run-gate.sh sed`: **GNU-gated 378 pass / 0 fail**. The one
  `win` row `sd056-version` reports `r_rc=0 c_rc=127` only because this
  worktree has no `build-vs/usr/bin/winuxcmd.exe` (C++ dispatcher not
  built) — a pre-existing environment gap, not a sed difference.
* `cargo test -p winux-regex`: all suites pass, including
  `tests/dfa_sed_equiv.rs` (new): DFA gate vs interpreter on 18 hand-picked
  sed shapes + 250 generated BRE patterns over a 311-line mixed corpus
  (empty, UTF-8, ill-formed bytes, embedded `\n`), the `-z` NUL record
  model, and the decline cases (`M` anchors, `-z`+`M` `.`, backrefs,
  oversized interval); it asserts the DFA actually engaged ≥50 patterns so
  the suite cannot go vacuous. `unify_smoke.rs::line_dfa_declines_dialect_nodes`
  was updated for the `DotRestricted` acceptance contract.
* `cargo test -p winux-cmds sed`: all pass, including
  `sed::tests::address_regex_dfa_filter_agrees_with_interpreter` (dot /
  anchor / word / backref / `-i` / `-z` / `N`-joined / `M` address shapes).

## Revert

The change is independently revertible: `git revert` this commit restores
`is_match_with` on the address path verbatim — `has_nfa`, the `dfa`/`dfa_eol`
fields, the `line_filter` flag, `dfa_sed_equiv.rs`, `sed_line_probe.rs` and
this document are additive, and the `DotRestricted` arm in `dfa.rs` only
widens which patterns *may* build a DFA (it changes no verdict by itself).
