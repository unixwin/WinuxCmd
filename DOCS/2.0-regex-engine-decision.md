# WinuxCmd 2.0 正则引擎决策（#1488）

> 决策文档，只裁定路线，不改任何实现代码。回答的问题：grep / sed / find
> 三个大件（inventory 实测 grep 3096 + sed 2802 + find 5578 = 11,476 行
> C++，其中 find 的正则只占 `-regex/-iregex` 一小面）的 rust2 重写被
> 「Rust 侧没有正则引擎」卡住，三个候选怎么选。
>
> 证据基线（全部本仓可复现）：
> - C++ 引擎：`src/utils/regex.cppm` @ main `a202eeb8`（1680 行）。
> - Rust 先例：`rust2/crates/winux-cmds/src/bre.rs`（382 行，服务
>   `tac.rs` 的 `-r` 分隔符）。
> - 消费方：`src/commands/{grep,sed,find,expr,csplit,diff,nl,less,tac}.cpp`。
> - regex crate 事实：docs.rs/regex/latest（2026-11 抓取），UNSUPPORTED
>   特性以官方文档为准。
> - 参照系：`target/uutils-audit/coreutils` @ `156d715`（uutils 如何选型）。
> - GNU grep dfasearch 架构为源码知识，本会话 savannah/GitHub 镜像均不可
>   达，**行号未在本会话重新核对**（§7 诚实声明）。

## 1. 决策问题

#1488 的形状契约（显式 IO、无进程级全局状态、机械替换、换完即弃、
std-only 零依赖）在 wave1-3b 已验证可走通（47 个命令）。wave4 的三个
大件全部需要一个正则引擎，而 Rust std 没有。三个候选：

| | 候选 | 一句话 |
|---|---|---|
| A | **移植自研** | 把 `src/utils/regex.cppm`（portable_regex，本仓 1.x 的 BRE/ERE 引擎）逐条语义移植成 Rust（`bre.rs` 先例证明这条路走得通） |
| B | **引入 regex crate** | 业界标杆，但打破 rust2「zero external dependencies, std only」政策（`rust2/README.md` 明文），需要 owner 豁免 |
| C | **FFI 复用 C++ 引擎** | rust2 命令经 ABI 调 portable_regex，工程量最小，但违背 2.0「摆脱 C++ 进程内耦合」方向 |

从消费方代码逐个核对（file:line 可查）：

| sed | BRE 默认；`-E/-r` ERE | **最重**：替换侧 `\1..\9`、`&` | 模式侧反引用 | 地址区间、`/I /M` 旗标、glibc 捕获选择语义（#1496）、空匹配迭代（#1284）、分隔符变体 | `sed.cpp:121-486` |

Perl 面只有 grep `-P` 一处，且今天就是由 PCRE2 承载（§5）。

## 3. 现有资产盘点

### 3.1 C++ portable_regex（`src/utils/regex.cppm`，1680 行）

能力清单（逐条读过源码）：

- 三语法 `Syntax::{Basic, Extended, Perl}`；BRE `\(\) \| \+ \? \{m,n\}`，
  ERE `() | + ? {m,n}`，两语法都支持 `\1..\9` 反引用、`\b \B \< \>` GNU
  词边界、`\s \S \w \W` 速记、POSIX 类 `[:alnum:]` 等、`[...]` 区间/取反/
  首 `]` 字面规则（regex.cppm:460-502, 584-625）。
- **glibc 对齐的捕获语义**：组按开括号顺序编号（#1496 修，
  regex.cppm:263-275）；重复体空迭代撤销对齐 glibc `update_regs`
  OP_CLOSE_SUBEXP 空分支（regex.cppm:1139-1233，注释逐句引 glibc
  regexec.c）；leftmost-longest（全状态集取 max pos，regex.cppm:660-670）。
- **抗灾设计**（#1495 家族）：按 (迭代数, 状态) 记忆化把 `\(.*\)*` 的
  2^n 分解压到多项式，步数/记忆/输出三重硬帽把残余爆炸转成保守
  no-match + `work_limit_exceeded` 旗标（regex.cppm:844-851）。
- **字面前滤快路**（#1531 修的 73x 慢）：anchored / 必需字面前缀
  memchr 跳跃 / 首字节 256 位集，全部是必要条件、解释器仍逐候选验证
  （regex.cppm:1247-1543）。
- UTF-8：`.` 和 `\b` 按整码点推进，CJK 不被切（D7，
  regex.cppm:65-123）。
- `Syntax::Perl` 委托 PCRE2（`PCRE2_DOLLAR_ENDONLY|UTF`，有 UCP 时加）
  regex.cppm:1613-1651；无 PCRE2 构建时报 "Perl matching not supported"。

问题史（每条都是 GNU 探针钉死的，等于已付的语义学费）：
#1339（sed 地址反斜杠）、#1284（空匹配多替换）、#1361/#1447（tac -r
BRE/空串）、#1119（`\r \t` 预解码）、#1495（指数回溯挂死）、#1496（glibc
捕获选择）、#1531（默认引擎 73x 慢 → 字面前滤）。**这七条全部沉淀在
当前引擎源码里，而不是在某人的记忆里**——这是候选 A 最大的一笔资产。

### 3.2 rust2 bre.rs（382 行，wave3a 先例）

支持：字面、`.`、类（区间/取反/首 `]`/反斜杠逃逸）、`* + ?`、`^ $`
锚、反斜杠字面、`\|` 交替；greedy 回溯（对这些算子形状与 POSIX
leftmost-longest 重合）。**不支持：`\(\)` 组、`\{m,n\}` 区间、反引用**
（bre.rs:16-19 明文）。

距离 grep 需求的差距：缺组/区间/反引用/捕获语义/UTF-8 整码点/词边界/
POSIX 类/i 大小写折叠——即 §2 刚需面里除「字面+类+星号」外的全部。
它证明的是**方法**（自研可走通、单命令引擎任务人日级），不是代码可
复用面。另外任务书里说「tac -r/csplit 已有自研 BRE」需更正：bre.rs
只服务 `tac.rs`（`grep -rn "bre::" rust2` 仅一处）；csplit 仍在 C++
侧用 portable_regex（inventory wave3，未移植）。

### 3.3 uutils 参照（`target/uutils-audit`）

uutils/coreutils 选了 `regex = "1.10.4"` + `fancy-regex 0.20`（其
Cargo.toml:100,116），用在 csplit/pr/ptx 的 pattern 解析。注意两点：
(1) uutils **不做 grep/sed/find**——crate 路线在三个最大正则消费方上
没有上游先例；(2) 我们的 #862/#492/#764/#765（csplit/ptx 正则行为）
恰恰是 uutils 用 crate 后仍要在我们这一层修 GNU 对齐的实例——crate
给了速度，没给 GNU 语义。

## 4. 候选 B（regex crate）调研

官方文档核实（docs.rs/regex/latest，2026-11）：

- **许可**：Apache-2.0 OR MIT 双许可，Unicode 表另按 Unicode License——
  许可无障碍。
- **反引用/环视：官方明文不支持**："lacks several features that are
  not known how to implement efficiently. This includes, but is not
  limited to, look-around and backreferences."（docs.rs/regex/latest）
  对 grep/sed 这是**硬缺口**，§2 刚需面直接踩中。
- **匹配语义：leftmost-first（Perl 式），非 POSIX leftmost-longest**。
  文档对交替明确写 "prefer x"（首支优先）。GNU grep/sed/expr/find 走
  glibc regex = leftmost-longest：`grep -o 'a\|ab'` 于 "ab" GNU 报
  "ab"，regex crate 报 "a"；sed `s/(a|ab)/X/`、`expr "ab" : ...` 同理。
  crate 不提供 POSIX 模式，也没有「枚举同起点全部匹配终点」的 API，
  补 longest 只能自建（倒排模式编译或逐起点重试），是又一个子工程。
- **unsafe**：本会话未能在官方页核到 forbid(unsafe) 声明（docs 页无此
  陈述）；已知其依赖 memchr 等内部含少量 unsafe。定级为「实现期复核
  deny.toml / cargo deny 结论」，不影响决策（许可与供应链才是政策点）。
- 依赖足迹：regex-syntax、regex-automata、aho-corasick、memchr 等
  ~4-10 个传递 crate，静态链接估 +1~2MB（参照：rust2 std 已 +1.0MB，
  REPLACEMENT-RECIPE §1）。

**混合方案评估**（B 的唯一语义可行形态）：regex crate 做主体 + 手写
反引用/longest 后处理。GNU grep 自己就是这个架构：
`src/dfasearch.c` GEAcompile 同时编译 DFA 与 regex_t，DFA 只做超集
预筛（dfa.c 对含反引用模式维护 nbackref，超集可能误报），命中后再用
regexec/re_search 全语义确认。这证明混合**可行**——但反过来读：
超集预筛便宜，**全语义确认器（捕获+longest+反引用）才是难的 80%**，
而那个确认器写完 ≈ 候选 A 的引擎本体。即 B 的混合形态下限 ≈ A 的
工程量，外加政策豁免、供应链与 crate 语义 glue（§3.3 的教训）。

## 5. 候选 C（FFI 复用 C++ 引擎）

工程量最小（ABI 封装 + 编组，估 2-4 人日），语义零风险（就是现在的
二进制在跑的东西）。但：

1. **违背 #1488「机械替换、换完即弃」**：`regex.cppm` 在每个正则命令
   移植后都删不掉，C++ 工具链（C++20 modules）与 cargo 构建永久互锁，
   wave4 之后每加一个正则相关命令都拖着整条 C++ modules 链。
2. **违背 2.0 立项前提**：#1488 的立项论据（niu#727 / #1487）就是 C++
   代码形状不配进程内复用；把**最复杂的语义组件**留在 C++ 侧跨 ABI
   调用，与方向相反。静态链接场景风险比当年 DLL 小，但「方向」是
   owner 2026-11-01 定调的，不是工程便利可以推翻的。
3. **形状契约摩擦**：`work_limit_exceeded` 是 thread_local（regex.cppm:50）
   ——2.0 契约「no process-global mutable state」要求编组进返回值，
   能做但每次都是陷阱位。
4. 热路径编组开销：grep 每（候选）行/区域一次跨界调用，量级可测，
   不致命但白付。

## 6. 对比与推荐

| 维度 | A 移植自研 | B regex crate | C FFI C++ |
|---|---|---|---|
| BRE/ERE/反引用/捕获/glibc longest | 全有（已 GNU 钉死） | **反引用硬缺、longest 硬缺**，需混合 | 全有 |
| grep `-P`（Perl） | 保留 PCRE2（见下） | crate 无环视/反引用，`-P` 仍需 fancy-regex 或 PCRE2 | 保留 PCRE2 |
| 工程量（引擎，不含各命令接线） | **8-12 人日**（详 §6.1） | 6-10 人日且下限=A（混合确认器） | 2-4 人日 |
| 语义风险 | 低-中（源码即规格，问题史已清） | **高**（新增 silent divergence 类，需逐类字节矩阵） | 低（短期） |
| 架构风险 | 低 | 低 | **高**（regex.cppm 永不可删、C++/cargo 构建互锁） |
| #1488 契约（显式 IO / 无全局 / 换完即弃） | 兼容（移植时把 thread_local 改返回值字段） | 需 owner 豁免 std-only 政策 + 供应链治理 | **不兼容**（换完即弃被永久打破） |
| 性能 | 字面前滤已达 #1531 验收；重扫描工况弱于 crate DFA（估 5-20x，可后续加 must 分析） | 最强 | 同 A（加编组税） |
| 依赖 | 零（std-only 保持） | +4~10 crate、+1~2MB、豁免 | 零新增（C++ 侧已有 PCRE2 FetchContent） |

### 推荐：A —— 把 portable_regex 逐条语义移植为 rust2 内的 `winux-regex`（std-only）

理由：

1. **语义资产只能随源码走**。七条 GNU 探针修出来的行为（§3.1 问题史）
   是 1.x 对 #1462 审计承诺的 parity 本体；机械替换的三道门里第三道
   「与前 exe 逐字节等价」用 A 天然可过，用 B 等于把已清零的语义风险
   账本重新开张。
2. **B 的可行形态下限就是 A**。反引用 + longest 逼出混合引擎，混合里
   的全语义确认器 ≈ A 本体，crate 只省下解释器循环的活，却引入政策
   豁免 + 供应链 + glue。除非性能门（§6.2）实测逼出需要 crate 的
   DFA 吞吐，否则 B 不划算。
3. **C 换来 2-4 人日，卖掉的是 2.0 的终态**。wave4 恰恰是「命令库化」
   的验收波；引擎留在 C++ 侧意味着 rust2 永远不是完整命令库。
4. **`-P` 裁定点（推荐保持现状形状）**：PCRE2 今天就是 C++ 构建的
   FetchContent 固定 tarball（pcre2-10.47，SHA256 钉死，CMakeLists.txt:203-217），
   默认 ON、纯 C ABI、无 CRT 环境耦合。2.0 里 `-P` 继续静态链 PCRE2
   ——这与「不引 Rust 生态依赖」不冲突（PCRE2 是既有原生依赖，且 crate
   路线也提供不了 `-P`）。不引 PCRE2 的构建维持现状降级报错
   （regex.cppm:1653-1656 行为）。此点请 owner 单独确认。

### 6.2 复审触发条件（写给未来的自己）

若 wave4 差分门出现 (a) 引擎吞吐在实际用户工况不达标（#1531 式实测：
同一批真实文件 × 真实模式族，与 exe 版逐字节等价前提下计时），或
(b) 移植后某类语义反复发散，则回到本单复审：届时只允许以 GNU 形态
混合引入 crate（crate 做预滤 DFA、本引擎做语义 oracle），**永不以
crate 为语义来源**。

## 8. Owner 裁定点（本单请求裁定的问题）

1. **引擎路线**：是否采纳候选 A（移植 portable_regex → `winux-regex`，
