# WinuxCmd 2.0 — StdinMeta 的 ABI 通道设计（ABI v4 输入元数据）

**状态：设计稿（design-only）。本文件不实现、不提交、不推送、不切分支。**
本稿的任何结论都要等 ABI v3 的验收与归属裁定落地后才可能转为代码；
在裁定之前，本文只作为 v3/v4 的输入材料。

**基线**

| 对象 | 位置 | 说明 |
|---|---|---|
| 产品主线 | `origin/main = 6d8980cc` | ABI **v2**（`winuxcmd_run` / `winuxcmd_run_stream`） |
| ABI v3 | `origin/rust2/stdout-stream-v3 @ a3a99abe` | `winuxcmd_run_io` + 写回调；**未接受** |
| tail 注入 | **已含于 6d8980cc**（`5c6d5116`；树与 `origin/rust2/tail-follow @ ae59632f` 相同） | `StdinMeta { kind, follow_path }`，driver 合成 |
| I18N 宿主接缝 | `7a24b01c`（在 6d8980cc 之后落到远端 main） | `Ctx.host: &dyn HostServices`、`message()` |

**依赖关系（必须显式记录）**

1. 本设计以 **ABI v3 的 io 表**为底座。v3 若被否、被改写或被拆成别的形态，
   v4 的结构定义要跟着重画：要么在 v4 里直接包含输出写回调（版本读作
   2→4，见 §6.2 末尾），要么退化为"纯输入通道"的增量。无论哪种，本稿的
   缺省语义、谎报契约与所有权结论都不变（见 §6.1、§8-D1）。
2. broken→141 归属（host 拥有 / command 拥有 / B+）**不在本稿裁定范围**。
   本稿只论证：无论选哪种归属，stdin 元数据通道的形态不变，且**必须与输出
   状态回调同表**（§5）。
3. 因此本稿**不触发实现**；它定义的是"如果 v3 通过，v4 应该长什么样"，
   以及"如果 v3 不通过，哪些结论仍然成立"。

## 1. 问题：ABI 路径拿不到 stdin 分类

### 1.1 现状链路

tail 的 follow 语义需要 GNU 从 `fstat(0)` 读到的两个事实：stdin 的**类别**
（普通文件 / 管道 / 控制台 / 字符设备）和普通文件 stdin 的**可跟随路径**。
库层已经把这两个事实收敛成注入值：

- `rust2/crates/winux-cmds/src/tail.rs:635` `pub struct StdinMeta { kind, follow_path }`
- `tail.rs:646` `StdinMeta::pipe_stream()` —— 注册表默认值
- `tail/sys.rs:35-47` `StdinKind { Disk, Pipe, Console, CharDev, Unknown }`
- `tail/follow.rs:438-448` `ignore_fifo_and_pipe`：`Pipe | Unknown` 从 follow 集丢弃

但**只有 driver 直接 dispatch 这一条路**把真实分类送进去了：

```rust
// rust2/crates/winuxcmd-driver/src/main.rs:196（6d8980cc 与 ae59632f 同树）
let status = if name == "tail" {
    let meta = tail_stdin_meta();                 // 读进程 stdin 句柄
    winux_cmds::tail::tail_with_meta(&args, &mut io, &ctx, &meta)
} else {
    winux_cmds::dispatch(&name, &args, &mut io, &ctx)
};
```

注册表本身只有 `fn(&[OsString], &mut Io, &Ctx) -> CmdResult`
（`winux-cmds/src/lib.rs:175`），`tail_cmd` 永远用 `pipe_stream()` 默认值
（`tail.rs:654-655`）。于是：

| 入口 | stdin 分类来源 | `tail -f - < file` 的实际行为 |
|---|---|---|
| driver 直接 dispatch | `tail_stdin_meta()`（进程句柄） | 按 Disk 跟随（GNU 语义） |
| `driver --abi`（v1） | 无 → `pipe_stream()` | 当作有限流，忽略 `-f` |
| `driver --abi-stream`（v2） | 无 → `pipe_stream()` | 同上 |
| C++ 桥（生产路径，v1/v2） | 无 → `pipe_stream()` | 同上 |

这不是理论问题：`tail -f -` 在 **生产路径（桥）** 上会退化成
"dump 后退出"，而 gate 只证明了 driver 直连路径
（`rust2/gate/wire/tail-follow.sh` 全部走 direct）。也就是说，tail 的
follow 虽已合入，**同一命令在两条宿主路径上的语义却不一致**。

需要强调：**这个缺口在基线 6d8980cc 上已经存在**（StdinMeta 注入提交
`5c6d5116` 已合入；`origin/rust2/tail-follow @ ae59632f` 与其树相同，
不是"待合入的新分支"）。因此本设计不是为某个分支补漏，而是在给已经
落地的注入模型补上 ABI 出口。

### 1.2 问题不是 tail 专属

`fstat(0)`/`isatty(0)` 这一族事实至少还有这些未来消费者：

- `find` 的 `-ok`/警告面（现有 C++ 版本用 `_isatty(_fileno(stdin))`，
  `src/commands/find.cpp:2490`）；
- 需要区分"从管道读"与"从终端读"来决定缓冲/提示的命令；
- 任何要复刻 GNU `isatty` 分支的命令。

所以通道应命名为**输入元数据（input metadata）**，而不是"tail 的私有参数"。

### 1.3 设计要解决的三件事

1. **通道**：宿主如何把分类与 follow 路径交给库，且不把进程句柄泄进库；
2. **缺省**：宿主不说时，库用什么语义（必须永不挂起、且与 v1/v2 字节等价）；
3. **归属**：这份"进程真实 IO 事实"由谁负责，与 broken→141 的归属如何共存。

## 2. 设计约束（不可谈判）

| 编号 | 约束 | 来源 |
|---|---|---|
| K1 | 库内**禁止**读进程 stdin（无 `GetStdHandle`、无 fd 0、无 `as_raw_handle`） | #1487 红线；tail/sys.rs 模块头已写明 |
| K2 | **禁止进程全局状态**：不得用环境变量、thread-local、全局注册表传分类 | #1488「ABI 面只传显式句柄/缓冲，不传环境状态」 |
| K3 | ABI 只传**显式值**；回调只在调用者线程同步执行 | v2/v3 既有契约 |
| K4 | v1/v2（以及 v3 若被接受）的符号与语义**不变** | 版本演进规则 |
| K5 | 缺省路径必须**永不挂起**：宿主不表态时，最坏结果是"少跟一个文件"，不是"永远等" | 见 §4.1 |
| K6 | 库是静态链接、桥用 `!=` 做版本相等门，因此库/桥必须同批构建 | `rust2_bridge.cppm:143-150` |
| K7 | 元数据是**一次性快照**，一次运行内不得变化 | GNU 的 `fstat(0)` 也只在启动时读一次 |

K2 值得展开：分类看起来像"环境状态"，其实不是——它是宿主对自己注入的
那组句柄的**描述**，与 argv/env/cwd 同级。放进 `Ctx`/host 表正是为了让它
随调用走，而不是随进程走。

## 3. 通道设计：两个方案

I18N lane 已经提出 `winuxcmd_host_v4`（含 message 回调）作为 v4 的宿主服务表。
本稿把它当作既有提案，只增加 **stdin 元数据**这一项，并比较两种加法。

### 3.1 方案 A：`winuxcmd_host_v4` 加 `stdin_meta` 回调（推荐）

宿主提供"按需填充"的回调；库在命令第一次询问输入元数据时调用它，
拿到值后复制成库内的 `StdinMeta`（含 `PathBuf`），回调返回后宿主可立即释放
自己的存储。

```c
/* 0 = filled; 1 = decline (library uses its pipe default);
 * <0 = host failure (the run returns 125). Called at most once per run. */
typedef int winuxcmd_stdin_meta_fn(void* user_data,
                                   struct winuxcmd_stdin_meta* out);
```

关键性质：

- **按需**：只有真正询问的命令（tail）触发；其余 50 个已接线命令
  （`CMakeLists.txt:76` 的 `WINUXCMD_RUST2_COMMANDS`，tail 尚不在其中）
  不会为 `GetFileType` / `GetFinalPathNameByHandleW` 付启动开销。
- **有"拒绝"通道**：`1` 明确表示"我知道自己不知道"，与"宿主出错"（`<0`）
  分开；前者落到缺省语义，后者是边界违约。
- **与既有 `HostServices` 接缝同构**：`message(key) -> Option<&str>` 也是
  "问一次、可拒绝"的形状（`rust2/crates/winux-core/src/host.rs:14-19`）。
- **演进**：以后要加 socket 类、终端尺寸、输入偏移等事实，只加方法/字段，
  不必再开新版本号（配合 §3.4 的 `size` 协商）。

### 3.2 方案 B：`winuxcmd_io_v4` / host 结构体内联字段

宿主在调用前把值直接填进表：

```c
struct winuxcmd_io_v4 {
  /* v3 的全部成员 ... */
  unsigned stdin_kind;          /* 0 = unspecified */
  const unsigned short* stdin_path;  /* UTF-16 */
  size_t stdin_path_len;
};
```

优点：没有回调、没有重入问题、测试断言直白、宿主编译器能静态检查字段。
缺点：

1. 没有"拒绝 vs 失败"的区分——只能靠 `kind == 0` 表达"不知道"，
   宿主读句柄失败与"不适用"无法区分，诊断能力弱；
2. 内联值在调用前就固定，若宿主想"只在命令需要时才算"，只能自己在
   调用点按 `name` 做特判——**把命令知识又推回宿主**，正是现状 driver
   `name == "tail"` 特例的翻版；
3. 与 `HostServices` 的方法式接缝不一致，库内要么把值塞进 `Ctx` 的
   普通字段（类型下移问题仍在），要么让命令直接读表（层次更差）；
4. 结构体每加一项都要重算 `size`/偏移，虽然可行，但审计面是"值"
   而不是"服务"，谎报无法定位到具体回调。

### 3.3 对比

| 维度 | A. host_v4 + `stdin_meta` 回调 | B. io 结构体内联字段 |
|---|---|---|
| 宿主计算时机 | 首次询问时（懒） | 调用前（急切） |
| 非 tail 命令开销 | 0 | 0（可填 0 跳过）~ 一次系统调用（若宿主统一预填） |
| "不知道"与"出错"分离 | 有（`1` vs `<0`） | 无 |
| 命令知识是否回流宿主 | 否 | 容易（宿主按 name 特判） |
| 与 `HostServices::message` 接缝 | 同构 | 异构 |
| 结构演进 | 加可选回调即可 | 每次加字段，重算布局 |
| 重入/时序风险 | 有（需明确一次性与线程规则） | 无 |
| 实现量 | 中（回调 + 一次复制） | 低 |
| 谎报审计 | 定位到单个回调 | 定位到字段，弱 |
| v1/v2/v3 兼容 | NULL 表 = 全缺省 | 新结构体，旧宿主不传 = 全缺省 |
| 与 I18N lane 的 v4 合并 | 同一张表 | 会分裂成两张表 |

### 3.4 裁定建议：A，但保留 B 的"零成本"性质

推荐 A。决定性理由不是"回调更优雅"，而是：

- 输入分类**只有少数命令需要**，且计算不免费（`GetFinalPathNameByHandleW`
  需要 32 KiB 缓冲，见 driver `main.rs:72-80`）。懒调用把成本限定在消费者身上。
- `1`/`<0` 的二分让"宿主老实说不知道"成为**一等语义**，而不是靠 0 值猜。
- 与 I18N lane 的 message 回调共享同一张表、同一套 `size` 协商，
  避免出现两个 v4。

同时接受 B 的两个好性质：**缺省零成本**（NULL 回调 = 不调用）和
**宿主侧可静态检查**（字段显式，编译器能查；建议 header 附带一个最小宿主
示例）。

### 3.5 建议的 v4 表（草案）

```c
/* ABI v4 stdin classification values (stable; 0 = unspecified). */
#define WINUXCMD_STDIN_UNSPECIFIED 0u
#define WINUXCMD_STDIN_PIPE        1u
#define WINUXCMD_STDIN_DISK        2u
#define WINUXCMD_STDIN_CONSOLE     3u
#define WINUXCMD_STDIN_CHARDEV     4u
#define WINUXCMD_STDIN_UNKNOWN     5u

struct winuxcmd_stdin_meta {
  unsigned kind;               /* WINUXCMD_STDIN_* */
  unsigned reserved;           /* must be 0 */
  const unsigned short* path;  /* UTF-16, borrowed for this call; may be NULL */
  size_t path_len;             /* UTF-16 code units, no terminator required */
};

typedef int winuxcmd_stdin_meta_fn(void* user_data,
                                   struct winuxcmd_stdin_meta* out);

struct winuxcmd_host_v4 {
  size_t size;                  /* sizeof(struct winuxcmd_host_v4) */
  unsigned flags;               /* WINUXCMD_IO_STDOUT_LINE_BUFFERED */
  /* --- v3 io, by value --- */
  winuxcmd_stream_read_fn*  stdin_read;   void* stdin_user_data;
  winuxcmd_stream_write_fn* stdout_write; void* stdout_user_data;
  winuxcmd_stream_write_fn* stderr_write; void* stderr_user_data;
  /* --- v4: input facts --- */
  winuxcmd_stdin_meta_fn* stdin_meta;     void* stdin_meta_user_data;
  /* --- v4: host services (I18N lane) --- */
  /* winuxcmd_message_fn* message;  void* message_user_data;
   * 签名与命名以 I18N lane 的 v4 提案为准；本稿只要求它与 stdin_meta
   * 同表、可独立为 NULL。 */
};

int winuxcmd_run_host_v4(const char* name, int argc, const char* const* argv,
                         const char* const* envp, const char* cwd,
                         const struct winuxcmd_host_v4* host);
```

说明：

- `size` 放在首位，允许"老库读新表"（只读 `min(size, sizeof)` 内的字段）
  与"新库读老表"（缺失尾部按 NULL/0 处理）。
- `kind` 用 `unsigned` 宏而非 C enum，避免不同编译器 enum 宽度的差异；
  Rust 侧 `#[repr(C)]` 用 `u32` 对齐。
- `path` 用 `unsigned short*` 而不是 `wchar_t*`：MSVC 上 `wchar_t` 是 16 位，
  但 header 明确"plain C types only"，用固定宽度类型才能钉死布局。
- 布局按 MSVC/默认 8 字节对齐，**不得**加 `#pragma pack`；Rust 侧
  `#[repr(C)]` 与之匹配。`size` 是 `sizeof`，不是手写常量。

Rust 侧的落点：`winuxcmd-ffi` 里用一个 `WinuxcmdHostV4` 适配器包住 C 表，
在入口构造 `HostServices`（`message` + `stdin_meta`），通过
`Ctx::with_host` 注入 dispatch。适配器**缓存** `stdin_meta` 结果，保证
一次 run 内 C 回调至多发生一次；命令只见 trait，不见 C 表。

### 3.6 语义细则

| 项 | 规则 | 理由 |
|---|---|---|
| 调用次数 | 每次 run **至多一次** | 快照语义，K7 |
| 调用时机 | 命令首次询问时（推荐懒式）；不得在改过 stdin 偏移后调用 | 与 GNU `fstat(0)` 启动期读取等价 |
| 表生命周期 | `host` 及其 `user_data` 在**整个 run 期间**有效 | 懒式回调可能晚于入口发生 |
| 回调副作用 | 不得读取 stdin 字节、不得重入库、不得改句柄文件指针 | 否则改变消费偏移/破坏单线程模型 |
| 线程 | 调用者线程、同步；不得重入库 | 与 v2/v3 回调同一模型 |
| 所有权 | `out->path` 在回调返回前有效；库立即复制进 `PathBuf` | 宿主无需保活 |
| 编码 | UTF-16（`path_len` 计数，无需 NUL） | 见 §3.7 |
| `kind` 未知值 | 按 `PIPE` 处理（向前兼容），不报 125 | 见 §3.8 |
| `kind` 非 DISK 且 `path != NULL` | 保留字段，库忽略 | 为未来类别留位 |
| 返回 `1` | 库用缺省（pipe） | 宿主诚实拒绝 |
| 返回 `<0` | run 返回 125（边界违约），不打印新消息 | 与 NULL name/cwd 的 125 约定一致 |
| 表为 NULL | 全缺省 | v1/v2 字节等价 |

### 3.7 路径为什么用 UTF-16

现有 ABI 的 argv/env/cwd 都是 UTF-8 C 字符串，路径**故意不一致**：

- 分类来自 `GetFinalPathNameByHandleW`，输出是 UTF-16；
- driver 现在先 `String::from_utf16_lossy` 再 `PathBuf::from`
  （`main.rs:72-80`）——**已经在边界上引入了有损转换**：非法代理项会被
  替换成 U+FFFD，随后 `File::open` 打开的是另一个名字（或失败→parked）。
- Rust 侧 `OsString::from_wide` 可以无损承载任意 u16 序列，正好匹配
  Windows 路径的"非文本"本质。

代价：header 多一种字符串形态，宿主需要多写几行。收益：follow 目标不会
因为编码往返而漂移；这也是"宿主谎报"之外唯一可能让 `tail -f -` 跟错文件的
技术原因。若 owner 坚持全 UTF-8，则必须在契约里写明"路径必须能无损转
UTF-8，否则宿主应传 NULL"，并接受 NTFS 非 BMP/孤立代理项路径的退化。

### 3.8 未知 `kind` 值：降解而不是 125

| 选择 | 后果 |
|---|---|
| 125（严格） | 未来 v5 宿主加一个 `SOCKET` 类别，所有 v4 库立刻拒绝服务 |
| 按 PIPE 处理（推荐） | 新类别在旧库上退化为"忽略 -f"，不挂起、不破坏其他命令 |

ABI 边界的默认原则应是"向前兼容地退化"，因为宿主与库可以不同批构建
（第三方嵌入者）。真正的宿主 bug（返回 `<0`）仍然 125。

## 4. 缺省语义与显式性边界

### 4.1 缺省 = pipe（GNU `ignore_fifo_and_pipe`）

当回调缺失、返回 `1`、或 `kind == UNSPECIFIED` 时，库使用
`StdinMeta::pipe_stream()`：`Pipe` + 无 follow 路径。

三条理由：

1. **事实正确**：v1 交来一整块缓冲，v2/v3 交来一个 pull 流——对库而言都是
   **有限字节流**，也就是 GNU 的 pipe/FIFO 类。pipe_stream 是"诚实的描述"，
   不是保守猜测（tail.rs:624-634 的注释已经这么写）。
2. **永不挂起**（K5）：Disk 类可能让 `tail -f` 永远运行。缺省绝不能是 Disk。
3. **字节等价**：这正是今天注册表的默认值，所以 NULL 表的 v4 与 v1/v2/v3
   行为逐字节相同，回归面最小。

注意 `Unknown` 与 `Pipe` 在 follow 集里行为相同（`follow.rs:444`），差别只在
"宿主明确说不知道"与"流语义"的区分；缺省仍选 `Pipe`，让 `Unknown` 只作为
宿主的显式声明存在。

### 4.2 各 kind 的行为表

| kind | 库内映射 | `tail -f -` 行为 | GNU 锚点 |
|---|---|---|---|
| `UNSPECIFIED` / 缺失 | Pipe | dump 后退出，`-f` 被忽略，rc 0 | `printf x \| tail -f` |
| `PIPE` | Pipe | 同上 | `ignore_fifo_and_pipe`（tail.c） |
| `DISK` + path | Disk | dump 后按描述符 follow，从已消费偏移续读 | `fstat(0)` → `S_ISREG` |
| `DISK` + NULL | Disk | dump 后 parked，直到 `--pid` 死亡；不读新数据 | 无直接对应（宿主无法命名文件） |
| `CONSOLE` | Console | 非 blocking 形态打印 warning；单输入时进入 blocking 读 | `isatty(0)` |
| `CHARDEV` | CharDev | 视作已打开但永不产出（如 NUL） | `/dev/null` |
| `UNKNOWN` | Unknown | 同 Pipe（从 follow 集丢弃） | 无法分类 |

"已消费偏移"不在元数据里：它是命令自己通过注入的 `io.stdin` 读掉的字节数
（tail.rs:624-634）。这是刻意的——宿主不应替命令记账，否则 v1（整块）与
v2（分段）两条路径会得到不同的偏移。

### 4.3 显式性边界：宿主谎报的行为契约

库**没有办法验证**分类（K1：不能自己 `fstat(0)`）。因此"谎报"不是
未定义行为，而是**由注入值完全决定的确定行为**。契约必须把它写死：

| 宿主声明 | 真实情况 | 库的可观察行为 | 风险 |
|---|---|---|---|
| Pipe/Unknown | 普通文件 | 当作有限流：dump 后退出（GNU 会跟随） | 功能退化，不挂起 |
| Disk + 正确 path | 同一普通文件，流从偏移 0 开始 | GNU 等价跟随 | 正确 |
| Disk + 指向别的文件 | 任意 | 初次 dump 来自 stdin 流，后续追加来自另一个文件 | **静默拼接，数据错位**（禁止） |
| Disk + path 无法打开 | 任意 | 落入 parked，直到 `--pid` 死亡 | 看起来"卡住"，但符合已文档化的 GNU 时长语义 |
| Disk + 指向管道/NUL | 管道/字符设备 | 轮询一个永不变的"文件"，直到被信号终止 | **可能永久运行** |
| Console | 管道/文件 | 多打一条 warning；blocking 读到 EOF | 文案/时序噪音，不挂起 |
| CharDev | 普通文件 | 当作永不产出的设备，不跟随 | 功能退化 |

由此得到**宿主唯一义务（H1）**：

> `follow_path` 必须是"`stdin_read` 所交付字节流的上游文件"，且该流必须从
> 文件偏移 0 开始、与文件当时的头部逐字节一致。做不到就传 `kind = PIPE`
> 或 `kind = DISK, path = NULL`，**不得猜路径**。

H1 的三种合法来源：

1. 对**同一个句柄**调用 `GetFinalPathNameByHandleW`（driver/桥今天的做法）；
2. 宿主自己打开文件并把它同时作为 stdin 注入（偏移已知为 0）；
3. 无法证明时拒绝（返回 `1`）。

**禁止**用 `cwd + "-"`、命令行参数、环境变量等推导路径——那会产生
"数据错位"那一行。

### 4.4 不可验证性必须被承认，而不是被掩盖

设计上**不做**运行时一致性检查（例如打开 path 比对 file id），因为：

- 库没有 stdin 句柄可比（K1），比对只能拿"刚打开的文件"与"另一个刚打开
  的文件"比，恒真；
- 真做校验会引入一次额外打开 + 失败路径，把"宿主 bug"变成"命令随机报错"。

替代方案是把不可验证性**转成可测试性**：§7 的谎报矩阵把每种组合固定成
gate 行，宿主侧（桥/driver）各自对自己的分类做单元测试。这也是
broken→141 备忘录里"归属一旦下放，必须逐命令有 GNU 对拍"的同一逻辑。

### 4.5 反模式（明确不做）

| 反模式 | 为什么不行 |
|---|---|
| 回调缺失时库内 `GetStdHandle` 兜底 | 违反 K1；让 ABI 路径永远测不到真实分支 |
| 用 `WINUXCMD_STDIN_KIND` 环境变量传分类 | 进程全局状态（K2），且 env 是命令可见数据，会被 `env`/`printenv` 泄漏 |
| 用 stdout 的 141 表示 stdin 分类失败 | 混淆两个通道（§5.5） |
| 让桥按命令名决定是否填元数据 | 命令知识回流宿主；新增消费者就要改桥 |
| 把"已消费偏移"也放进元数据 | 宿主无法在流式路径上准确知道；由命令自己的读计数才与 v1/v2 一致 |

## 5. 与 broken→141 归属裁定的关系

### 5.1 为什么必须同表

broken→141 与 stdin 元数据看起来无关，其实是同一个问题的两面：
**"进程真实 IO 事实"由谁拥有、如何送达库**。

- 输出侧：某次写失败到底是"读端没了（broken pipe）"还是"其他写错误"，
  只有宿主知道（`is_stdout_pipe_closed()` / `is_stdout_write_failed()`，
  v3 分支的 `stdout_write_cb`，`rust2_bridge.cppm:284-303`）。
- 输入侧：stdin 到底是文件、管道还是终端，只有宿主知道。

如果两者放在不同的表/不同的版本号里，就会出现"宿主升级了一半"的状态：
输出事实已按 v4 语义解释，输入事实还按 v3 缺省——同一进程对库的描述
自相矛盾。用一张 `size` 协商的表，才能保证**一次运行内宿主对库的事实
描述是原子的**（规则 C2/C3）。

对"一张表会把 I18N 与 IO 的版本绑死"的反驳：表内的每个回调都**可独立为
NULL**，且 `size` 协商允许老库只读前缀字段。宿主可以先只填 `stdin_meta`
（message 留 NULL，走英文 fallback），I18N lane 之后再填 message——两者
共享的是**布局与协商机制**，不是**采纳节奏**。反过来，若拆成两张表，
"半升级"就无从检测：没有人能在一个地方回答"这次运行宿主到底承诺了什么"。

### 5.2 三层所有权

| 层 | 所有者 | 内容 | 通道 |
|---|---|---|---|
| 事实（fact） | **宿主** | stdin 类别/路径；stdout 是否 broken/closed；读到的字节 | `stdin_meta`、`stdin_read`、`stdout_write` 返回值 |
| 策略（policy） | **命令** | `-f` 是否适用于该 stdin 类（GNU `ignore_fifo_and_pipe`）；EPIPE 是否致命（`tee -p`、`xargs` 123-127） | 命令内部逻辑 + 返回值/opt-out 标志 |
| 翻译（translation） | **桥/宿主边界** | 把"stdout 写失败"翻译成 141 或"write error"；把 124/125 透传 | 桥的 `run_io` 尾部映射 |

这张表就是本稿对"谁拥有进程真实 IO 事实"的回答：**宿主拥有事实，
命令拥有策略，桥只做翻译**。归属争议的实质是第三行**是否允许无条件翻译**，
而不是事实由谁提供。

### 5.3 三种裁定下的 v4 表形态

| 裁定 | 输出侧含义 | v4 表要不要改 | stdin 通道 |
|---|---|---|---|
| A：host 拥有（现状 v3） | 任意 stdout `-1` → 141，无 opt-out | 不改（沿用 v3 语义） | 不变 |
| B：command 拥有 | 库返回最终状态，宿主不覆盖 | 不改；v3 的 `stdout_write` 返回值仅作诊断 | 不变 |
| B+：host 默认 + command opt-out（备忘录建议） | 默认 141；命令声明已处理则保留自身状态 | `flags` 加一位或返回哨兵（**另一个 lane 定义**） | 不变 |

结论：**stdin 元数据与 141 归属正交**。这很重要，因为它意味着：

- tail 的输入元数据不必等 141 裁定就能在 v3 底座上设计（但仍要等 v3 是否
  被接受，因为底座本身未定）；
- 反过来，不能用"宿主更懂 IO"来论证 141 应该无条件覆盖——输入事实的
  信任模型（§4.3）恰恰说明：宿主可以**说谎**，所以凡是能下放给命令的
  策略（EPIPE 处置）就应下放，凡是不可能下放的事实（stdin 类别）才留在宿主。

### 5.4 一致性规则

| 编号 | 规则 | 违反后果 |
|---|---|---|
| C1 | 同一 run 的所有 IO 事实来自同一个宿主对象 | 半升级/自相矛盾 |
| C2 | 同一张表、同一 `size` 协商 | 两个版本号，无法审计 |
| C3 | 任一通道可独立为 NULL，但不得"半答"（例如声明 Disk 却不给流） | 未定义拼接（§4.3） |
| C4 | 库不得由 stdin 类别反推输出状态，也不得由输出状态反推 stdin 类别 | 141 误用（§5.5） |
| C5 | 全 NULL 表必须与 v1/v2 字节等价 | 兼容性回归 |

### 5.5 状态码领地（不得混用）

| 状态 | 唯一含义 | 不得用于 |
|---|---|---|
| 141（128+13） | 进程因 SIGPIPE 死亡（stdout 读端消失） | stdin 分类失败、宿主拒绝提供元数据 |
| 124 | 宿主停止喂 stdin（timeout/interrupt） | 元数据缺失 |
| 125 | 边界违约（panic、句柄 IO 错、未知命令、无效宿主输入） | 普通命令错误 |
| `tee -p` 的 0 / `xargs` 的 123-127 | 命令自己的策略结果 | 被宿主改写 |

特别地：`stdin_meta` 回调返回 `1`（拒绝）**不是错误**，不得产生任何状态码；
返回 `<0` 才是 125。141 永远只能由 stdout 写事实触发。

## 6. 迁移路径

### 6.1 阶段

| 阶段 | 内容 | 是否动 ABI | 前置 |
|---|---|---|---|
| S0 现状 | driver 特例 + 注册表 pipe 默认；ABI 路径无法表达分类 | 否 | — |
| S1 库内接缝 | `StdinKind`/`StdinMeta` 下移到 `winux-core::host`；`HostServices` 增 `stdin_meta()`；tail 从 `ctx.host` 取；driver 实现该 trait；删掉 `name == "tail"` 特例 | **否** | I18N 的 `Ctx.host`（7a24b01c）先落地 |
| S2 加法 ABI | header + `winuxcmd_run_host_v4` 导出 + Rust 适配 + 测试；`winuxcmd_abi_version()` **暂不 bump** | 加法 | S1；v3 底座已定 |
| S3 桥采纳 | 桥用同一 `STD_INPUT_HANDLE` 分类；tail 走 v4 流式（避免 v1 整块 + 偏移问题）；库/桥/宏**同批** bump 到 4 | 是 | S2 + v3 已合入 |
| S4 清理 | `tail_with_meta` 收为测试/内部 API；README/recipe/gate 收尾 | 否 | S3 |

S1 是**最便宜的去风险步骤**，且不依赖 v3：它把"driver 特权路径"变成
"driver 是宿主的一个实现"，让 direct 与 ABI 两条路在库内走同一入口。
但它依赖 I18N 的 `Ctx.host` 先落地（6d8980cc 还没有这个字段；7a24b01c 才有）。
tail 代码本身已合入，所以不需要"先合 tail"：顺序是 I18N 接缝 → S1，
在 S1 里顺手修掉 `Ctx { cwd, env: &env }` 的旧字面量（与 I18N 提交的机械
迁移是同一处冲突）。

S2 的"暂不 bump"遵循仓库既有先例（`rust2/README.md:289-296`：v2 加法期间
版本号保持 1，桥采纳时才 bump 到 2）。原因很具体：`abi_version_ok` 是
`!=` 相等门（`rust2_bridge.cppm:143-150`），只改 Rust 侧会让所有已接线命令
在桥上直接失败。静态链接没有运行时符号探测，所以"加法 + 同批 bump"是唯一
安全的节奏。

S3 的一个细节：桥现有的 stdin 句柄来自
`GetStdHandle(STD_INPUT_HANDLE)`（`rust2_bridge.cppm:252`）。分类必须用
**同一个句柄**，并在 `set_stdin_binary` / 任何 seek 之前做；若桥走 v1 整块
路径，则要求整块内容就是文件从 0 开始的头部，否则按 H1 拒绝（返回 `1`）。
推荐 tail 一律走 v4 流式，彻底绕开整块缓冲的偏移假设。

「加法」= S2 落地时；「采纳」= S3 同批修改。

**版本号读法**：上表的 `3→4` 以"v3 被接受"为前提。若 v3 被否、v4 直接落在
v2 上，则所有 `3→4` 读作 `2→4`，且 v4 结构必须**自行包含输出写回调**
（不能引用一个未被接受的 `winuxcmd_io_v3`）；触点清单其余各项不变。
这正是 §8-D1 必须先裁的原因——版本号只是表象，结构底座才是成本。

明确**不需要**改的：`CMakeLists.txt` 源列表（只改 header/现有 TU）、
`scripts/i18n_batch.py`（无新消息）、打包脚本（无新增二进制）。

### 6.3 rebase/合并顺序

1. broken→141 裁定（owner）→ v3 定稿；
2. v3 合入（含 `rust2_bridge.cppm` 的 `run_io`）；
3. I18N 的 `Ctx.host` 接缝（7a24b01c）进入工作基线——tail 已合入，
   但它的 driver 仍用 `Ctx { cwd, env: &env }` 旧字面量，需在 S1 一并
   改为 `Ctx::new`；
4. S1 → S2 → S3。

反序（先 v4 后 v3）会迫使 v4 结构在 v3 未定时重画，成本更高。
注意：`origin/rust2/tail-follow @ ae59632f` 与已合入的 `5c6d5116` 树相同，
不存在"再合一次 tail 分支"的步骤；若有人从旧分支继续开发，必须先对齐
`5c6d5116`，否则会重复提交同一棵子树。

### 6.4 回滚

- S1 可单独回滚（纯 Rust 内部 + driver），ABI 无感。
- S2 只加符号，不改变 v1-v3；回滚 = 删符号（静态链接下无运行时残留）。
- S3 是唯一改变生产行为的提交：回滚点应包含桥的 `stdin_meta = NULL`
  （即退回"忽略 -f"），且版本号与宏一起回退。禁止只回退一侧（`!=` 门会
  让所有命令 125）。

| D11 | B+ 的 opt-out 形态（`flags` 位 vs 返回哨兵） | 另一个 lane 决定；本设计不依赖 | owner |
| D12 | 是否为第三方宿主提供契约测试套件 | 建议在 `tests/` 放最小 C 宿主桩，不发布 DLL | ABI owner |

---

## 9. 结论

1. **通道应放在 `winuxcmd_host_v4` 的回调里，而不是内联字段**：输入分类只有
   少数命令需要、计算不免费、且需要"拒绝/失败"二分；回调与 I18N 的
   `HostServices::message` 同构，也避免把命令知识推回宿主。
2. **缺省必须是 pipe**：它与 v1/v2 的有限流事实一致、与注册表今天的行为
   字节等价、且永不挂起。宿主不表态时 `tail -f -` 退化为"dump 后退出"，
   而不是永久轮询。
3. **宿主拥有事实、命令拥有策略、桥只做翻译**。stdin 元数据与 broken→141
   是同一条所有权原则的两个实例，因此必须同表、同版本、原子快照；但
   **输入通道与 141 归属正交**，v4 的表形态在 A/B/B+ 三种裁定下都不变。
4. **谎报无法验证，只能契约化 + 固定成 gate**：最危险的一行是
   "Disk + 指向别的文件"，会静默拼接两份数据；因此规定 `follow_path` 只能
   来自同一句柄或可证明的偏移 0，做不到就拒绝。
5. **迁移分四步，S1 不依赖 v3**：先把 driver 特例消灭（库内接缝），再加
   符号（版本暂不 bump），桥采纳时同批 bump 到 4。版本触点清单共 16 行
   （§6.2），其中第 16 行 I18N 在本设计下为"无新增消息"。
6. **本稿不触发实现**：v3 未裁定前，任何 v4 代码都会在底座变化时返工。
   下一步只应发生两件事：owner 回答 §8 的 D1/D2/D4，以及 v3 的归属裁定。
