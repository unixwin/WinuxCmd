## 2. 关键事实：四仓的正则引擎没有一个是可移植的 Rust 引擎

这是本次审计对 regex 决策（§6）最重要的输入：

1. **grep 仓**：BRE/ERE/Perl 三种模式全部走 `onig`/`onig_sys`——Oniguruma
   的 **C 绑定**（`matcher.rs:8-23`，含手写 onig_sys raw wrapper 和
   `Send` unsafe impl）。Rust 侧只有匹配调度、行缓冲、上下文缓冲。
   **grep 仓没有自带 POSIX BRE/ERE + 反引用的 Rust 引擎**，"移植 grep 仓
   引擎"这个选项不存在——引擎本体是 C。
2. **findutils 仓**：同样 onig（`matchers/regex.rs:9`）。
3. **sed 仓**：策略是"BRE 翻译成 ERE + 双 crate"：`bre_to_ere()`
   （`compiler.rs:591`，含 `^` 在 `\(`、`\|` 后仍是锚点等边角）把 BRE
   规整为 ERE 交给 `regex::bytes`；检测到 `\1..\9` 反引用时整体回退
   `fancy-regex`（回溯引擎，支持 backreference）。这是**两个外部 crate**
   的组合，不是自研引擎；但它的 BRE→ERE 翻译器和"快路径/慢路径分流"
   架构是可以借的算法。
4. **diffutils 仓**：`bre.rs`（360 行，`pub mod bre`）是四仓中唯一的
   自含 POSIX BRE 处理层，做法同样是**翻译到 regex crate**。它服务的
   选项面窄（diff `-F` 等），不含反引用捕获提取的完整语义。

结论：**四个兄弟仓全部把正则难题外包给外部 crate 或 C 库，与 2.0
std-only 零依赖政策不兼容的部分恰恰是它们的核心依赖。** 兄弟仓提供的
是「翻译层/分流架构」的可借算法，不是引擎本身。

## 3. IO 形态与 #1488 显式 IO 契约

四仓全部是**进程级 stdio**：`std::env::args_os()` 取参、
`std::io::stdout()` 直写（grep 2 处、sed 3 处直写点但 fast_io 大块缓冲、
findutils 18 处、diffutils 63 处）。没有任何一仓提供可注入 writer/reader
的库形态。因此**整体采用（路线 C）时，#1488 的显式 IO 契约需要重写每仓
的输出层**；grep 的 searcher.rs（789 行）把匹配、输出、上下文缓冲耦合在
一起，改造面最大。diffutils 的 lib 分层（`pub mod unified_diff` 等纯生成
器）改造面最小。

## 4. 语义对照抽样（三方 × 8 case/命令）

原始输出：`target/uutils-siblings/sampling/threeway_all.txt`。case 面向
本仓已知风险区：BRE 反引用、ERE 区间、`-o` span、空匹配迭代、`y` 命令、
`gI` 旗标、`-printf`、目录递归、`cmp` 字节报告。

**grep（8/8 三方一致）**：BRE 反引用 `\(abc\)\1`、ERE `a{2,}`、
`-o '[0-9]\+'`、BRE `\+`、`-w`、UTF-8 `.`（整码点计数）、`-E` 交替、
`-F` 字面。uutils grep 在这些面与 GNU 逐字节一致——Oniguruma 底座可靠。

**sed（8/8 三方一致）**：替换反引用 `\2 \1`、`-E a+`、地址区间 `2,4d`、
`gI` 旗标、`y///`、空匹配 `s/b*/X/g`（→`XaXcX`）、分隔符变体 `s|/a|/z|`、
`-n '$p'`。uutils sed 的 bre_to_ere + 双引擎策略在本抽样无差分。

**find（6/8 一致）**：`-name`、`-type f -o -type d` 优先级、`-maxdepth`、
`-printf %p:%y`、`-regextype posix-extended -regex`、`-exec {} \;`、
`-empty` 全部一致。两处差分：
- **路径分隔符自相矛盾**：walk 输出 `tree\a.txt`（反斜杠），而同一仓的
  `-printf '%p'` 输出 `tree/a.txt`（正斜杠）。GNU 恒为 `/`。这与
  `docs/windows-path-contract.md` 的 verbatim 契约直接相关，若整体采用
  必须修 walkdir 层的路径拼接。
- `-newer` 对不存在引用文件的报错措辞三方各异（GNU：`‘...’: No such
  file or directory`；我们：`cannot read reference file for -newer`；
  uu：本地化中文 + `(os error 2)`）——措辞级，非语义级。

**diff 族（uu 7/8，我们 6/8）**：
- **uu diffutils 缺 `-i`**（`--ignore-case`）：`unrecognized option '-i'`，
  exit 2。GNU 与我们的 C++ 都支持。这是 uu diffutils 的真实功能缺口，
  #1575 式"借算法"时应避开该选项的 theirs-侧实现、以 GNU 为准。
- `cmp` 字节报告：GNU/uu 均为 `differ: byte 7, line 2`，**我们的 C++ 是
  `differ: char 7, line 2`**——这是**本仓 1.x 的差分**（非 uu 问题），
  应记入我们的 compat 清单：`cmp.cpp` 的措辞需改为 `byte`。
- 目录递归头部：我们 C++ 打印冗余的
  `diff diff -r tree tree2 tree/a.txt tree2/a.txt`（双 `diff` + 全参数），
  GNU 是 `diff -r tree/sub/b.txt tree2/sub/b.txt`（仅差异文件对），
  uu 是 `diff -r tree\sub\b.txt tree2\sub\b.txt`（对但反斜杠）。同样记入
  本仓 1.x compat 清单（`diff.cpp` 目录递归头部措辞）。
- normal/unified/context 三格式逐字节一致（三方）。

抽样局限（诚实声明）：浅 clone 无法取历史；三方 8×4 case 是**抽样**，
不构成任何一方的完整兼容性证明；uu grep README 自述 v0.2.0 初版，其
`-P`/`-r`/上下文选项等未纳入本次抽样。

## 5. 三条路线的量化对比

| 维度 | A 自研移植（regex 决策 A 延伸） | B 逐仓借算法（#1575 先例） | C 整体采用兄弟仓 crate |
|---|---|---|---|
| 需新写代码量 | 最大：四命令全部重写（1.x C++ 基线 11,476 行，Rust 形态另计） | 中：借模块（sed compiler/processor ≈ 5,000 行级、diff 生成器 ≈ 4,000 行级、find matchers ≈ 3,000 行级）逐个移植并替换依赖 | 小：不改算法，只做 IO 契约适配 + 依赖治理 |
| 依赖足迹 | **0（std-only 达标）** | 0（借的模块替换 regex/fancy-regex/onig 为 portable_regex） | 119–167 传递包/仓，**且 grep/findutils 含 C 库 onig_sys**，直接违背 rust2 `zero external dependencies` |

| 维护耦合 | 无上游 | 低（快照移植，非依赖跟踪） | 高：四仓各自演进，版本钉死 119–167 包 |

## 6. 与 regex 决策（DOCS/2.0-regex-engine-decision.md）的联动结论

**维持推荐 A（移植 portable_regex），不改为"移植 grep 仓引擎"。**
理由：§2 已证 grep 仓的引擎是 Oniguruma C 绑定，不存在可移植的 Rust
引擎体。兄弟仓对 A 路线的**增量价值**是两个具体的移植参考件：

1. `sed` 仓 `bre_to_ere()`（`compiler.rs:591-850`）：现成的 BRE→ERE
   规整器，含 `^` 锚点上下文、单数字反引用非捕获组包裹等边角——
   portable_regex 移植时的**第三方言对照**（GNU C ↔ 1.x C++ ↔ uutils sed）。
2. `diffutils` 仓 `bre.rs`（360 行，MIT，`pub mod bre` 导出）：自含
   POSIX BRE → 内部表示翻译器，接口干净（`Bre::new/is_match`），可近乎
   整体借用（替换其 regex-crate 后端为 portable_regex）。

即：A 路线的表述从"移植 portable_regex（1.x C++ 引擎语义）"扩展为
"移植 portable_regex，BRE 解析层以 uutils sed `bre_to_ere` +
diffutils `bre.rs` 为交叉对照语料"。

## 7. 推荐与每命令路线表

**总推荐：B 为主（逐仓借算法，#1575 先例），A 承担正则引擎与骨架，
C 整体排除**（onig_sys C 依赖 + 119–167 传递包 + IO 重写 + Windows 缺口
四个成本叠起来，超过 B 的移植成本；且与 std-only 政策正面冲突）。

| 命令 | 路线 | 借用/参照来源 | 备注 |

2. 把 `target/uutils-siblings/sampling/` 的三方 case 纳入
   `tests/differential/corpus/` 的 grep/sed/find/diff 语料（四命令各
