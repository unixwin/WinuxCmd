## 2. 1.2.1（C++）行为对照

### 2.1 方法

- harness：`tools/matrix.py`（用例 `tools/cases_oldnew.py`）。
- 每个用例在**三个独立 fixture** 上跑（old/new/GNU 各一棵树），相对路径、`cwd=fixture 根`，防止旧侧写入污染新侧。
- 捕获 rc / stdout 字节 / stderr 字节 / 文件树快照（相对路径、类型、大小、sha256 前 16 位、链接目标）；沙箱绝对路径洗成 `<ROOT>`。
- GNU 侧 fixture 由同一份 op 列表生成（`base64 -d` 写字节），三边字节一致。
- 分类：`all-equal` / `gnu-fix`（new=GNU、old≠GNU）/ `platform`（old=new≠GNU）/ `new-deviation`（new 与 old、GNU 都不同）/ `regression`（old=GNU、new≠GNU）/ `old==new` 或 `volatile-field`（GNU 腿 N/A）。
- 证据：`old-vs-new/evidence/<case>/{old,new,gnu}.{out,err}` 与 `.tree`。

**覆盖说明**：任务列的 14 个命令中，`ls/rm/mv` 在本树 Rust 库里**没有实现**（registry 无这三个名字），没有 2.0 侧 → **N/A**；`wc/cat` 也没有 Rust 实现（不在 14 个里）。实际覆盖 **11 命令 × 20~26 例 = 245 例**：cp 24、ln 22、stat 21、du 21、df 22、grep 26、sed 24、find 22、sort 22、head 21、tail 20。

- 245 例里 **189 例三方逐字节全等**；grep/sed/sort/head/tail **全部 100% 对齐**，cp 23/24 全等（余 1 例是修正），stat 17/17（可比项）。

## 3. 性能（Release，64 MiB / 2000 文件）

### 3.1 方法

- harness `tools/perf.py` → `perf/perf.csv`；每组 warmup 一次后测 **3 次取中位数**（`*_min` 同时记录最小值）。
- 语料：`big.txt` 精确 64 MiB（64 字节定长记录，`MARKER` 每 997 行一次），Windows NTFS 与 WSL ext4 哈希一致（`6531d1c8…dd50`）；`tree/` = 200 目录 × 10 文件。
- Windows 输出→NUL，GNU→`/dev/null`。
- **两列 GNU**：`GNU ext4`（WSL 原生 ext4）、`GNU NTFS`（同一批 NTFS 文件经 `/mnt/c`，9p 开销）。两者都不是纯 CPU 时间；**跨文件系统的倍率不作为"超越/落后"结论**，只报量级。
- 2.0 分 `product`（产品 exe 实际走到的实现）与 `library`（Rust 库 dispatch）。采样命令中只有 find/grep/ln/sed/stat 已接线；**sort/cp/head/tail/du/df 仍是 C++**，所以 sort、cp 的 product 列≈1.x，library 列才是 2.0 的真实性能。

### 3.3 解读（如实）

1. **grep 与 sed 是换装收益最大的两条**：1.2.1 的 C++ 实现极慢（grep 字面 4.7 s，sed `-n /re/p` 5.9 s）；Rust 库分别 38 ms（123×）和 116 ms（50×）。产品已接线，用户可感知。
2. 但**对 GNU 仍是明显弱项**：grep 字面 12.7×、正则 60.6×（对 GNU ext4）；即便对读取同一 NTFS 文件的 GNU 也是 3.5× / 34.6×。这是引擎差距，不是 I/O。
3. **sort**：Rust 库 138.8 ms，1.2.1 C++ 11.7 s（**84×**）。但 **sort 尚未接线**，产品跑的仍是 10.2 s 的 C++——`cat|sort` 12.8 s 几乎全耗在这里。这是"接了线才有收益"的最典型一条。
4. **sed `s///`**：2.0 206 ms vs GNU ext4 243 ms（0.85×），但 GNU 经 9p 读同一 NTFS 文件是 4.9 s；所以"比 GNU 快"不能当结论，只能说与 GNU ext4 同量级。
5. find/cp/wc/cat：大多是个位数到亚秒级，对 GNU ext4 差 1.3~20×；cp-tree 的差主要是 per-file 元数据开销（GNU 在 9p 上更差到 30 s，说明 9p 完全不能用于 I/O 对比）。
6. 全部数字为 Release；Debug 数字未采用。

## 4. 边界用例

方法同 §2（`tools/cases_boundary.py`，55 例，每类 ≥5）；GNU 腿在无 POSIX 对应（长路径、junction、保留设备名）时标 `gnu="na"`，不做假比较。

| 类别 | 用例 | all-equal | old==new | old!=new | regression | gnu-fix |
|---|---|---|---|---|---|---|
| 长路径（绝对 305 字符） | 7 | 0 | 5 | 2 | 0 | 0 |
| Unicode（中文/emoji/希腊/组合） | 8 | 8 | 0 | 0 | 0 | 0 |
| CRLF / 混合换行 | 8 | 8 | 0 | 0 | 0 | 0 |
| NUL 字节（含保留设备名 2 例） | 10 | 8 | 2 | 0 | 0 | 0 |
| 空操作数 / 空模式 | 8 | 3 | 0 | 1 | 3 | 1 |
| 只读属性 | 8 | 7 | 0 | 1 | 0 | 0 |
| junction / LX link | 6 | 0 | 4 | 2 | 0 | 0 |

### 4.1 长路径（>MAX_PATH）——P1

- **`cp` 回归（确认）**：相对 269 字符 / 绝对 305 字符时，1.2.1 `cp` 成功（18 字节），**2.0 Rust `cp` 报 `No such file or directory` rc=1**；产品 exe 的 `cp` 仍是 C++，同样成功。
  手工复现（同目录同参数）：

  ```
  old (1.2.1): cp <305-char rel path> old-copy.txt  -> rc=0, 18 bytes
  new (driver): cp <same>              new-copy.txt  -> rc=1 cannot stat ... No such file or directory
  prod (2.0)  : cp <same>              prod-copy.txt -> rc=0, 18 bytes  (仍走 C++)
  ```

  同一路径上 `stat/head/grep/tail/find` 在 2.0 都正常，问题局限在 `cp`（原因推断：未走 `\\?\` 长路径前缀）。
- `du -a -b <长目录>`：1.2.1 只列前 6 层且大小全 0（自身降级失败），2.0 完整列出并包含 `long.txt`（但大小仍 0，`-b` 口径问题同 §2.3）。2.0 优于 1.2.1，但都不正确。

### 4.2 Unicode / CRLF / NUL / 只读

- **Unicode 8/8 三方逐字节一致**（`中文文件.txt`、`emoji😀.txt`、`Ω_greek.txt`、组合字符、嵌套中文目录）；argv 与 stdout 都 UTF-8 直通。
- **CRLF/LF 8/8 一致**：`head/tail -c/sed/grep/sort` 都保留 CR。
- **NUL 字节 8/8 一致**：`grep -a`、`sed`、`head`、`tail -c`、`sort`、`cp` 的二进制直通与 GNU 相同。
- `nul.dat`/`nul09`/`nul10`：**DOS 保留设备名**，Windows 两侧都打不开（GNU 视为普通文件），单列 gnu=N/A。
- **只读属性**：`cp`、`cp -f`、`sed -i`、`ln`、`stat %a`、`du` 共 7 例三方一致；`cp -r . backup` 两代都拒绝，只有报错文本不同（2.0 GNU 化），文件树一致。

### 4.3 空操作数（2.0 的系统性差异）

| 用例 | 1.2.1 | 2.0 | GNU |
|---|---|---|---|
| `head ""` | rc=1 `cannot open '' for reading: No such file or directory` | rc=1 `error reading '': Is a directory` | 同 1.2.1 |
| `stat -c '%n\|%F' ""` | rc=1 `cannot statx '': No such file or directory` | **rc=0，输出 `\|directory`** | 同 1.2.1 |
| `ln "" h` | rc=1 `failed to access '': No such file or directory` | rc=1 `: hard link not allowed for directory` | 同 1.2.1 |
| `cp a.txt ""` | rc=1 `Invalid argument` | rc=1 `No such file or directory`（=GNU） | 同 2.0 |

相邻但非空操作数的一处修正：`cp -i a.txt copy.txt`（stdin=`n`）1.2.1 打印提示后仍覆盖（rc=0），2.0 按 `n` 放弃（rc=1，=GNU）。

结论：2.0 把**空字符串路径解析成了 cwd**，导致 `head/stat/ln` 的错误语义偏离 1.2.1 与 GNU（`stat ""` 甚至成功）。`cp` 两处反而是 gnu-fix。

### 4.4 junction / LX link

- 本机无 symlink 特权：`ln -s`、LX symlink **SKIP**。
- junction（`mklink /J`，无需特权）：
  - `stat -c %F holder/junc`：1.2.1 `directory`，**2.0 `symbolic link`**（2.0 把 reparse point 识别为链接）——行为变化，需在文档/测试固定。
  - `cp -r holder holder2`：1.2.1 试图重建 junction→EPERM 失败；**2.0 直接解引用，把目标内容复制成真实目录（rc=0，多出 `holder2/junc/t.txt`）**；GNU 复制链接本身。
  - `head`（穿过 junction）、`du`、`find -maxdepth 2`：两代一致。

## 5. 与 uutils coreutils 的三方对照

### 5.1 可得性

- uutils Windows 发行 zip 下载三次中断（curl 28/56），改用 **`cargo install coreutils --version 0.12.0`** 成功（crates.io 可用，编译 3m44s）。
- **限制**：该 Windows 构建**不含 `stat`、`du`、`df`**（`coreutils.exe stat/du/df` → `coreutils: unknown program`）。这三条记 **N/A**，不是"行为不同"。
- 实际可比：**cp、ln、head、tail、sort、wc、cat**（7 命令，56 例）。
- WinuxCmd 侧：Rust 库命令用 release driver；`wc`/`cat` 用 2.0 产品 exe（C++）。

### 5.2 结果（56 例）

| 分类 | 例数 |
|---|---|
| WinuxCmd=GNU 且 uutils=GNU | **47** |
| WinuxCmd=GNU，uutils≠GNU | 6 |
| 三方都不同 | 2 |
| **WinuxCmd≠GNU，GNU=uutils** | **1** |

逐命令：

| 命令 | 例 | 三方一致 | WinuxCmd=GNU/uutils≠ | 三方不同 | WinuxCmd 单独偏离 |
|---|---|---|---|---|---|
| head | 8 | 8 | 0 | 0 | 0 |
| tail | 8 | 8 | 0 | 0 | 0 |
| wc | 8 | 8 | 0 | 0 | 0 |
| sort | 8 | 7 | 1 | 0 | 0 |
| cat | 8 | 7 | 1 | 0 | 0 |
| cp | 8 | 6 | 2 | 0 | 0 |
| ln | 8 | 3 | 2 | 2 | 1 |

### 5.3 关键差异

1. **`ln -f a.txt hard_a.txt`（WinuxCmd 单独偏离）**：GNU 与 uutils 都成功替换，WinuxCmd 2.0 报 same-file rc=1（1.2.1 也成功）。→ 与 §2.3(a) 同一问题，建议修。
2. `ln a.txt hard_a.txt`（无 `-f`，目标存在）：三方 rc=1，文本各异（`are the same file` / `File exists` / `Already exists`）。
3. `ln -s`：uutils 与 WinuxCmd 都 EPERM；uutils 的错误串是**系统本地化 GBK**（`客户端没有所需的特权`），写进管道会变乱码；WinuxCmd 是英文。uutils 的问题，仅记录。

## 6. 结论与放行建议

### 6.1 可以放行

- **gate 全量 3635 行 0 fail / 0 pending**（88 命令，含 posix 30 例）。
- 245 例对照中 **189 例三方逐字节全等**；grep/sed/sort/head/tail 全部 100%，cp 23/24 全等 + 1 修正，stat 17/17。
- Unicode、CRLF、NUL、只读属性边界全部干净；`cp -i` 与 `cp a.txt ""` 两处是相对 1.2.1 的**修正**。
- 性能：Rust grep/sed/sort 相对 1.2.1 有 23×~123× 提升；产品已接线的 grep/sed 用户可立即感知。

### 6.2 换装前应修 / 应决策（按优先级）

| 优先级 | 事项 | 证据 |
|---|---|---|
| **P1** | `cp` 不支持 >MAX_PATH（1.2.1 支持；产品现走 C++，接线后会暴露） | §4.1，`boundary/evidence/002-lp03` |
| **P1** | `df -l` / `df -T` 不可用（rc=1） | §2.3，`097-df10`、`099-df12` |
| **P1** | `ln -f` / `ln -i` 对同 inode 目标报 same-file（1.2.1 与 GNU 都正常） | §2.3(a)，`027-ln04`、`040-ln17` |
| **P1** | `du -a` 硬链接重复计数；`du -d 0` 当无限深 | `071-du05`、`085-du19` |
| **P2** | 空字符串路径被解析成 cwd（`stat ""` 成功、`head ""`/`ln ""` 错误语义偏离） | §4.3 |
| **P2** | `cp -r` 对 junction 解引用、`stat %F` 对 junction 报 symbolic link（行为变更需固定） | §4.4 |
| **P2** | `df` 挂载点 `C:` vs `C:\`、卷枚举多出 W:/Y: | §2.3 |
| **P2** | **sort/cp/head/tail/du/df 尚未接线**：产品仍跑 C++，sort 的 84× 收益拿不到 | §3.3 |
| **P3** | gate posix root 撞名陷阱；CI 未认领 cp/find/grep/sed 六张表 | §1.3 |
| **P3** | grep 正则比 GNU 慢 60×（跨 FS，量级仍是问题） | §3.2 |

### 6.3 N/A 与不可断言项

- `ls/rm/mv`：Rust 库无实现，无 2.0 侧（N/A）。
- uutils 的 `stat/du/df`：该 Windows 构建不含这三个程序（N/A）。
- symlink（`ln -s`、`-L` 跟随、LX symlink）：宿主无特权，SKIP；junction 单独覆盖。
- 性能为**跨文件系统**测量，两列 GNU 都列出；不据此宣称"超越 GNU"。
- 1.2.1 与 `38b3751d` 之间存在版本漂移；`new` 与 `old` 的差异可能包含 1.3~1.9 的 C++ 改动，方向判断以"谁与 GNU 一致"为准。已接线命令在同一 commit 上无法产出纯 C++ 对照（CMake 禁止 dual-track），这是本报告的固有限制。
- 不涉及 wpm 打包、安装布局、I18N 发布。
