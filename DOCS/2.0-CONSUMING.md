# Consuming WinuxCmd 2.0

This page is for products that want to *use* WinuxCmd rather than rebuild its
commands: a shell (rubash/niubash/bash), a CI image, an editor plugin, or an
installer that needs GNU-shaped tools on Windows.

There are three supported consumption surfaces. They are independent; pick the
one that matches how much control you need over stdin/stdout and the process
model.

| Surface | What you get | Process model | Use when |
|---|---|---|---|
| A. PATH applets | `ls.exe`, `grep.exe`, ... as hardlinks of one `winuxcmd.exe` | one process per command, inherits real stdio | a shell or build system expects executables on `PATH` |
| B. Direct dispatch | `winuxcmd <applet> [args...]` | same image, same process | a script can prefix commands, or you want one stable entry point |
| C. C ABI (staticlib) | `winuxcmd_run` / `winuxcmd_run_stream` | in-process, explicit handles only | a host (shell, editor, service) wants no child process and full control of IO |

---

## A. PATH applets (the multicall layout)

`winuxcmd.exe` dispatches on `argv[0]`. The Windows installer and wpm create
`<root>\usr\bin\<applet>.exe` as **hardlinks** to the same image, so a shell
that already searches `PATH` needs no changes.

Verify what a consumer sees:

```powershell
winuxcmd --version
winuxcmd --list-all | Select-Object -First 5
Get-Item (Get-Command ls).Source | Select-Object FullName, LinkType
# LinkType: HardLink, and (Get-Item ...).Target is winuxcmd.exe
```

A bash product should prepend the applet directory, not copy binaries:

```bash
# bash-product.sh — see examples/consume/bash-product.sh
export PATH="/c/Program Files/WinuxCmd/usr/bin:$PATH"
command -v ls          # .../usr/bin/ls.exe
ls -l /etc | head -3
```

Rules that matter for a shell product:

- **Do not put private DLLs in the applet directory.** `usr\bin` is on `PATH`;
  a flat package that drops `libcrypto.dll` there is a packaging bug. WinuxCmd
  itself is one self-contained image.
- **Hardlinks, not copies.** A copy costs a second image open and a second AV
  decision (see `DOCS/perf-1396/README.md`); a hardlink shares the inode.
- **One owner per name.** Two packages cannot both own `usr\bin\ls.exe`;
  wpm refuses the second install. Resolve overlaps in the package manifest,
  not with `PATH` order.
- `winuxcmd --list-all` is the authoritative command list for a given build;
  editions differ (see `DOCS/2.0-edition-audit.md`).

## B. Direct dispatch (one entry point)

If the caller can prefix commands, `winuxcmd <applet>` avoids maintaining a
link farm:

```bash
winux() { "${WINUXCMD_BIN:-winuxcmd.exe}" "$@"; }

winux ls -la
winux grep -rn "TODO" src/
printf 'b\na\n' | winux sort
```

This is also the portable form for environments where creating hardlinks is
not allowed (locked-down CI, some network shares).

## C. C ABI: embedding the command library

`winuxcmd_ffi` is a **staticlib** folded into the consumer's link, not a DLL.
That is deliberate: the FFI post-mortem (#1487, niubash#727) traced the
DLL-path failures to load-time CRT stdio binding in a separately linked
module. One image, one CRT, no load-time binding.

The ABI is explicit-handle only: argv, envp, cwd and stdin are passed in;
stdout/stderr come back as Rust-owned buffers. No CRT fd, no process stdio,
and no environment lookups cross the boundary.

```c
#include "rust2_abi.h"

winuxcmd_cbuf out = {0}, err = {0};
const char* envp[] = {"LC_ALL=C", NULL};
int rc = winuxcmd_run("sort", 0, NULL, envp, "C:\\work",
                      (const unsigned char*)"b\na\n", 4, &out, &err);
if (rc == 0) fwrite(out.ptr, 1, out.len, stdout);
winuxcmd_free_buf(&out);
winuxcmd_free_buf(&err);
```

Only commands in the rust2 registry are reachable this way;
`winuxcmd_has_command("name")` answers membership before you run. Commands
that are still C++-only (see `DOCS/2.0-inventory.tsv`) are not in the library
yet.

For streaming stdin (pipes larger than memory, `tail -f`, `xargs`), use
`winuxcmd_run_stream` with a pull callback; the host returns `>0` bytes,
`0` for EOF, `-1` for timeout/interrupt (the run returns **124**), `-2` for a
read failure.

Build and link (MSVC, from a configured build tree):

```bat
cl /nologo /I src\shared examples\consume\abi-consumer.cpp ^
   build-vs\rust2-target\x86_64-pc-windows-msvc\release\winuxcmd_ffi.lib ^
   advapi32.lib kernel32.lib ntdll.lib userenv.lib ws2_32.lib dbghelp.lib ^
   wtsapi32.lib netapi32.lib
```

The native library list comes from
`cargo rustc -p winuxcmd-ffi --lib --crate-type staticlib -- --print native-static-libs`;
re-run it after a Rust dependency change.

ABI guarantees a host can rely on:

- `winuxcmd_abi_version()` must equal `WINUXCMD_RUST2_ABI_VERSION` (2 today);
  refuse to run on mismatch.
- `winuxcmd_has_command(name)` answers registry membership without running.
- A Rust panic is caught at the boundary and returned as **125**; it never
  unwinds into the host.
- Buffers are host-freed with `winuxcmd_free_buf`; the host owns its input
  buffers for the duration of the call only.
- Calls are synchronous on the caller's thread; the stream callback runs on
  that same thread.

`examples/consume/abi-consumer.cpp` is a complete, compilable example.

## Which surface should a shell product use?

- **bash/rubash/niubash running external commands**: A. It is what the shell
  already does; no code change beyond `PATH`.
- **A shell that wants to replace fork/exec for builtins**: C. The library
  form avoids a child process and lets the shell own the pipes.
- **A build system or CI image**: A or B; B is the least invasive when the
  image cannot create links.

The three surfaces share one command registry and one set of gate tables, so a
command behaves the same whether it is reached through a hardlink, through
`winuxcmd <applet>`, or through the C ABI.
