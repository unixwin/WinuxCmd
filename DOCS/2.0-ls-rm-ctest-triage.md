## 1. Why the gate was green while ctest was red

The gate and ctest cover disjoint surfaces:

- `rust2/gate/cases/ls.tsv` has **no permission, device, junction, dired,
  POSIXLY_CORRECT, or colour-padding rows** (`grep -c rwx` = 0).
- The host cannot build the symlink fixture
  (`symlink-capability=no`, final gate log line 6), so all LX-reparse rows
  are skipped rather than failed.
- The GNU side runs on DrvFs, where GNU also sees `0777` for every file;
  the Windows mode model (#1777) is invisible to a DrvFs oracle.
- The gate's locale is `C.UTF-8`; the old test that pinned C-locale byte
  escaping could never be exercised by it.
- `rm` has **no gate case table** at all (`no case table for rm` in the
  final gate log); its two reds are only visible in ctest.

So "gate green" is not evidence for the 35 rows; it is orthogonal.

## 2. Method

1. Rebuilt `winuxcmd.exe` + `winuxcmd-tests.exe` at `290cac83` and re-ran
   `ctest -R "^(ls|rm)\."` to reproduce exactly 35 reds.
2. For each red, extracted the exact argv/Pipeline call from the test,
   ran the same argv against the product (`build-vs/usr/bin/ls.exe`,
   `rm.exe`) and against GNU 9.4 in WSL, with the same fixture shape
   (TempDir on `D:`, junctions via the test helper's `mklink /j`, LX
   reparse points via `wsl ln -s`).
3. Classified:
   - **C1 library defect** — GNU (or the product's documented value model)
     does what the test expects; the rust2 library does not. Test not
     touched, recorded for the lane.
   - **C2 1.x assertion rot** — GNU 9.4 does *not* do what the 1.x test
     pinned; the test is corrected or deleted with the probe in the
     commit.
   - **C3 platform subset** — the behaviour is unreachable on Windows;
     the assertion is pinned to the documented subset with a
     `DOCS/2.0-MIGRATION.md §6` citation.

## 4. Class 1 residual: 25 reds (library lane, no test changes)

### 4.1 Shared Windows mode model (#1777) — 5 tests
`ls_long_format_uses_windows_writable_permission_shape_for_regular_file`,
`..._executable_extension_file_is_755_like_stat`,
`..._windows_writable_permission_shape_for_directory`,
`ls_block_size_scales_s_and_total_on_windows`,
`ls_k_option_scales_s_and_total_on_windows`.

`rust2/crates/winux-cmds/src/stat.rs::mode_word` is the canonical model:
character devices 0666, directories and `.exe/.com/.bat/.cmd` 0755, other
regulars 0644, `FILE_ATTRIBUTE_READONLY` clears the write bits.
`find -printf %m` and `stat -c %a` already return it; `ls.rs` still has
the pre-#1777 synthesis (`'x'` for every non-device, `'w'` triplet-wide
unless read-only). Port `mode_word` shape into `ls.rs` (the #1777 commit
`da0b448a` only patched the then-unwired C++ `ls.cpp`).

Note for the lane: tests #15/#16 fail only on the long-format permission
prefix; the block-size arithmetic they assert is already correct.

### 4.2 Junction / symlink operand handling — 3 tests
`ls_long_format_reports_directory_junction_size_as_zero`,
`ls_quote_name_quotes_long_format_symlink_target_too`,
`ls_long_format_classify_marks_directory_symlink_name_not_target`.

- `-l <junction-to-dir>` must print the link row. Today it follows the
  junction, tries to list the target, and prints `total 0` (or an error).
  GNU prints the link for `-l` and lists contents only in the default
  short format. (Tests for `-ld`, `-la`, and short-format operands pass.)
- `-lF` must put the indicator on the displayed target (`dirlink ->
  target/`), never turn the link name into `dirlink/`.

### 4.3 Device-name synthesis (#1779) — 2 tests
`ls_long_format_lists_dev_null_as_char_device`,
`ls_long_format_lists_synthesized_devices_as_char_devices`.

`ls` maps `/dev/null` to the DOS name `nul`, reports it as a regular file
with 0777, and does not know `/dev/zero|random|urandom|full`; `stat`
already synthesizes all of them as `crw-rw-rw-`. Reuse `stat.rs`'s device
probe and keep the operand spelling in the output.

### 4.4 LX reparse points (#1639/#1640/#1642) — 6 tests
`ls_dereference_option_follows_lx_file_link_operand_issue1640`,
`..._lx_file_link_directory_entry_issue1640`,
`ls_directory_operand_lx_directory_link_lists_target_issue1640`,
`ls_dereference_option_lx_directory_link_self_is_directory_issue1640`,
`ls_recursive_dereference_lx_directory_link_lists_target_issue1640`,
`ls_group_directories_first_groups_lx_directory_link_issue1642`.

`ls` does not read the LX tag `0xA000001D` for `-L`/`-H`/`-R`: file links
become `cannot access`, directory links become `cannot open directory`,
and `-lL .` shows `l?????????` rows. The 1.x C++ body handled the tag; the
library header claims it, but the dereference path is missing.

### 4.5 Error-path spelling — 2 tests
`ls_group_directories_first_dangling_link_reports_and_groups_issue1642`,
`ls_dereference_dangling_entry_error_path_elides_dot_issue1640`.

`ls -L .` must elide the `.` directory component in the cannot-access
diagnostic (`'dangling'`, not `'./dangling'`; GNU `attach()` rule).

### 4.6 `ls.rs` option/diagnostic gaps — 5 tests
- `ls_sort_candidate_table_matches_coreutils_9_4` and
  `ls_color_attached_empty_is_invalid_issue1513`: an empty argmatch word
  is **ambiguous**, not invalid (`ambiguous argument '' for '--sort'` /
  `'--color'`). The `--color` test's rc is already corrected to GNU's 1.
- `ls_width_option_invalid_is_fatal_issue1536`: missing colon in
  `invalid line width: ‘abc’`.
- `ls_posixly_correct_stops_at_first_operand`,
  `ls_posixly_correct_empty_value_still_stops_at_first_operand`: with
  `POSIXLY_CORRECT` present (even empty), stop option scanning at the
  first operand; `--color=never` becomes an operand.

### 4.7 Shell-dialect and layout gaps — 2 tests
- `ls_mnt_drive_dialect_resolves`: a bare `/mnt/<drive>` must resolve to
  the drive root; `C:\` currently fails the attribute probe (same
  drive-root class as #1145, already special-cased for `/`).
- `ls_across_color_disables_tab_padding_issue1641`: `--color` sets
  `tabsize = 0`; grid padding must be spaces, not tabs.

## 6. Correction to the handoff note

The note said `rm file/` expecting `Not a directory` rc 1 while the
library returns silent rc 0 is a **real library defect**. Probe:

```
$ rm -r -f file.txt/   # GNU coreutils 9.4
$ echo $?
0
$ ls
file.txt
$ rm file.txt/
rm: cannot remove 'file.txt/': Not a directory
$ echo $?
1
```

`-f` suppresses the diagnostic by design. The test exercised the forced
form while asserting the unforced outcome. The product matches GNU in
both forms, so this row is class 2, not class 1.

## 7. Known, unasserted observations (for the lanes)

- `rm '*.txt'` on the product reports `... : Invalid argument`, GNU says
  `No such file or directory` (Win32 `ERROR_INVALID_NAME` mapping). The
  re-pinned test asserts only the literal-operand failure, not the errno
  reason, so it does not encode the wrong text. Candidate for the same
  lane as `ls`'s operand-wildcard ENOENT rule.
- The opt-in `WINUX_SHELL_GLOB=native` glob matcher has a separate bug:
  `a*` does not match `a.txt` because `wildcard_match` rejects a `.` at
  the start of the *remaining* name even after a literal prefix
  (`glob.rs`, the `'*'` arm). This is outside the GNU contract (the
  deleted tests were the only pins), but the extension lane should fix
  it or retire the matcher.
- The gate still has no `rm` case table (`no case table for rm`), so rm
  has no differential coverage at all. Worth a separate gate task.
